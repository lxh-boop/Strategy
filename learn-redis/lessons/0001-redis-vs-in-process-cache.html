Lesson 0001 · Redis

Redis 与你进程里那块缓存

预计 20 分钟 · 动手环境：官方沙盒（零安装） · 绑定 mission：多实例演进时亲手接入 Redis · 配套速查表

1 · 从你的代码讲起

你在 mysql-factor-data.service.ts 里手写了一个进程内缓存——历史上行情落库后不变，重复回测没必要反复打库：

// factor-agent-server/src/core/implementations/mysql-factor-data.service.ts（简化）
private readonly cache   = new Map<string, FactorCacheEntry>();    // LRU：命中删了重插，超容从队首删
private readonly inflight = new Map<string, Promise<unknown[]>>(); // 同 key 并发查询去重

private async query(sql, params) {
  const key = sql + '§' + JSON.stringify(params);
  const hit = this.cache.get(key);
  if (hit && Date.now() - hit.at < 10 * 60_000) return hit.rows;   // TTL 10 分钟
  // …未命中 → 打库 → 回插缓存
}

三层机制你都很熟：TTL（10 分钟兜底数据商修正）、LRU（200 条防内存膨胀）、inflight 去重（并发同查询搭车）。单实例下它工作得很好。

现在只问一个问题——如果明天起有两个实例跑这套代码（《并发治理方案》第八节的 100 人演进路径），这个 Map 会怎样？

单实例（今天）

所有请求共享同一块 Map：命中率稳定，同 key 并发必然搭车，重启丢缓存但很快热身回来。

两个实例（明天）

各自一块 Map：互不知晓。同一查询打两遍库；LRU 容量与热身成本 ×2；每次部署两块缓存同时清零。命中率不升反降。

进程内缓存的三个天然边界，全都来自同一个事实——它活在你的进程里：随进程生、随进程死、只有你的进程看得见。

2 · Redis 一句话定位

本课核心心智模型 Redis = 把你进程里那个 Map 搬进一个独立进程，让所有实例通过网络连上去共享同一块键空间。

四个事实支撑这个模型，每个都和进程内 Map 形成精确对照：

维度你的 MapRedis
生命周期随进程重启全丢独立进程；可选持久化，重启服务不丢缓存
可见范围仅本进程所有实例连同一块键空间
值类型任意对象引用有类型的：string / list / hash / set / zset…（本课只用 string）
并发模型你自己加闸（inflight）单线程事件循环，每条命令天然原子

「单线程」值得停一下：Redis 处理命令是逐条串行的，所以一条命令执行期间不会被别的命令插入。你在代码里用 inflight Map 手工解决的「check-then-set 竞态」，在 Redis 里往往一条原子命令就消失了。

3 · 本课命令面：7 条

所有类型里 string 是最常用的缓存形态（值可以是任意字节串，比如一段 JSON）。本课 7 条命令全部 O(1)：

命令作用对照你的代码
SET k v写键this.cache.set(key, …)
SET k v EX 600写键 + TTL，原子一步完成set + hit.at 时间戳两步合一
GET k读键（无则返回 nil）this.cache.get(key)
DEL k删键this.cache.delete(key)
EXISTS k键是否存在（0/1）this.cache.has(key)
EXPIRE k 600给已有键设 TTL—（你的 TTL 只能写入时定死）
TTL k看剩余秒数（-1 无 TTL / -2 键不存在）hit.at 的手工比对
一个容易误判的点 TTL 归零的那一刻，键不会被立刻从内存移除。Redis 以惰性删除为主（下次访问发现过期才删），后台再定期抽样补删。这和你代码里「过期条目不回插、下次重查」是同一种最终一致的口味——副作用都是过期数据可能短暂占着位置。

4 · 动手：把一条缓存键跑完一生

动手任务 · 约 8 分钟 打开 redis.io/try/sandbox（免安装免注册），按步骤执行。每步都给了你应该看到什么——对不上就停下来问 agent。
  1. 写入一条「因子缓存」，带 600 秒 TTL： 
    SET factor:PE:600030:20260930 '{"pe":21.4}' EX 600
    应看到：OK。注意值是 JSON 字符串——string 类型不关心内容结构。
  2. 从三个角度确认它存在： 
    EXISTS factor:PE:600030:20260930
TYPE  factor:PE:600030:20260930
GET   factor:PE:600030:20260930
    应看到：1、string、原样返回的 JSON。
  3. 看 TTL 在流动——连跑两次： 
    TTL factor:PE:600030:20260930
    两次结果不同、在递减（如 597 → 589）。TTL 是服务端时钟在走，不是你的代码在算 Date.now()。
  4. 看一条键真正过期。写一条只活 10 秒的，然后等它： 
    SET flash:demo ok EX 10
TTL flash:demo
（等 10 秒）
EXISTS flash:demo
GET   flash:demo
    应看到 0 和 nil。这就是缓存的完整一生：写入 → 存活 → 过期消失，全程无你的代码参与。
  5. 顺手体验原子计数器（string 类型内置整数语义）： 
    INCR demo:hits
INCR demo:hits
GET demo:hits
    应看到 1、2、"2"。两次 INCR 之间即使有一万个并发客户端，也不会丢计数——单线程原子性，无需你加闸。
  6. 清理现场： 
    DEL factor:PE:600030:20260930 demo:hits
    应看到 2（删除的键数）。

选做挑战（和你熟悉的限流退避同源）：用 SET rl:u1 1 EX 60 NX + INCR rl:u1 实现一个 60 秒窗口计数器。NX 的语义问 agent，两分钟讲清。

5 · 检索练习

不看上文，凭记忆答——答错可以换选项重试：

Q1 · 单实例下，把你的 LRU Map 原样搬到 Redis，下一次回测的缓存命中率会——

再想想：单实例下请求模式没变，只是缓存换了个存放位置，行为等价——还多付一次网络往返。Redis 的收益从第二个实例出现才开始。
对。命中率由请求模式决定，不由缓存位置决定。单实例迁移是纯开销（网络往返），收益要等第二个实例出现——这正是方案文档说「当前不引入」的原因。

Q2 · Redis 服务端处理命令的方式，最准确的说法是——

不对。回忆第 2 节的对照表：你在代码里手工解决的那类竞态，在 Redis 里为什么不需要手工解决？
对。单线程事件循环意味着命令逐条串行、天然原子。你的 inflight Map 解决的 check-then-set 竞态，在 Redis 里常被 SET NX、INCR 这类原子命令直接吸收。

Q3 · SET k v EX 600 之后客户端进程重启了三次，600 秒内 GET k 会——

回忆第 3 步动手观察：TTL 走的是谁的时钟？客户端进程的生死影响服务端的键吗？
对。TTL 与过期都记录在服务端，与任何客户端进程无关。这正是「你的 Map 一重启全丢」的反面——缓存可以活得比某次部署更久。

Q4 · 键的 TTL 归零的那一刻，Redis 会——

回忆「容易误判的点」那条提示框——惰性删除。你代码里过期条目的处理方式其实是同一个设计哲学。
对。惰性删除为主（下次访问发现过期才真删）+ 后台定期抽样补删。和你「过期条目不回插」的写法一样，都是用最终一致换实现简单——过期键会短暂占内存，靠定期抽样兜底。
