# 股票池筛选独立方案（pool 工具 + 句柄）

> 2026-10-21 grill 收口（用户逐项拍板），本文档即功能清单与改造方案，实施在同一分支进行、暂不提交。
> 决策记录见 ADR-0006，术语见 GLOSSARY「股票池筛选」簇。

## 一、背景与问题

行业筛选 476b220 落地后暴露架构问题：股票池的限定散落在两个引擎参数里（`industries` 行业名、`securityIds` 显式清单），且没有指数成分来源——用户说"只做沪深300"时 GLM 只能手拼 300 只清单（编造温床）或退化成全市场。行业走的是引擎内逐调仓日解析（`impl:246-251`），清单概念从未物化；显式清单则必然进 prompt。

用户定调（grill 结论）：

1. **股票池筛选独立成 GLM 工具**（不是参数泛化）：多条件、支持交并集。
2. **回测只接受股票代码序列**；筛选结果不进 prompt，GLM 只见摘要。
3. 只有行业、沪深300 这类**定义固定的集合**才算股票池筛选；"突破 60 日线才买"是条件，留在回测引擎逐调仓日判断（entryFilters 不动）。
4. **成员名单动态 PIT 跟随**（查证结论：聚宽 `get_index_stocks` 缺省回测当前日、果仁以消除存活偏差为卖点、静态快照=幸存者偏差虚高收益）。"定了不会变"落实为**筛选定义不变**。
5. 句柄存 MySQL（会话级），保存策略时规格快照随 config 走。
6. 筛选工具免确认（纯只读）；每日选股对称接入。

## 二、设计

### 核心流

```
GLM ──screen_stock_pool({groups:[...]})──▶ 免确认直跑：
                                            组内并集 ∪、组间交集 ∩ 解析（当前时点）
                                            ▶ MySQL pool_refs 存【规格+摘要+成员数】→ poolId
                                            ▶ 回执只给 GLM：poolId + 摘要 + 成员数
GLM ──run_strategy_backtest({poolId,...})─▶ 确认卡显示摘要（"有色金属∩沪深300（147 只）"）
                                            ▶ tools 节点解析 poolId → 规格
                                            ▶ 引擎逐调仓日 PIT 解析成员（行业/指数成分跟随调样）
                                            ▶ 与 securityIds 取交集 → 选股域
```

关键点：**句柄里存的是规格不是清单**——所以引擎能逐调仓日重新解析实现动态跟随；清单本身只存在于引擎内部，全程不进 prompt。

### 筛选规格（两层结构）

```ts
type PoolGroup =
  | { kind: 'industry'; names: string[] }   // 申万一级行业，组内并集
  | { kind: 'index'; codes: string[] }      // 指数成分（000300.SH 等），组内并集
  | { kind: 'list'; ids: string[] };        // 用户点名清单，组内并集
type PoolSpec = PoolGroup[];                // 组间交集；空数组 = 全市场
```

示例：`[{industry:[有色金属,黄金]}, {index:[000300.SH]}]` =（有色∪黄金）∩ 沪深300。

### 指数成分数据（idx_member）

- Tushare `index_weight` 按月快照拉取（2005 至今），存 `(index_code, con_code, trade_date)`；PIT 查询 = 取 `≤ asOf` 最近一个快照的成分（不依赖 in_date 质量）。
- 与行业同库（SQL/industry/industry.duckdb，新表 `idx_member`），下载并入 `download-industry.mjs`（默认 000300.SH/000905.SH/000016.SH，可参数化扩）。
- 数据源缺失 fail fast（同 sw_member 模式）；用户已定调"数据库是唯一数据源，不需要考虑"——基础设施就位即可。

### 句柄存储（pool_refs）

`alphasage_user.pool_refs`：`id`（p+随机 12 位）、`conversation_id`、`spec_json`、`summary`、`member_count`、`created_at`。会话维度（UserStore 方法不带 userId，约定例外已注释）；保存策略时规格快照随 `StrategyRunConfig.pool` 落库，重跑不依赖句柄存活。

### 展示（回测卡一定正确）

引擎入参 `pool: { summary, memberCount, groups }` 由编排层填充，**摘要即参数的一部分**——三处"股票池"行内联三元直读 `p.pool?.summary`，零查询零传参链。形态：

| 场景 | 股票池行 |
|---|---|
| poolId | `有色金属∩沪深300（147 只）`（摘要从参数直读） |
| securityIds | `N 只` |
| pool/清单同传 | `摘要 ∩ N 只清单` |
| 都缺省 | `全市场` |

### 退役

- `industries` 参数全线删除（tool-specs/类型/归一化/引擎分支/每日选股/卡片），行业降级为 pool 规格的一种来源——双轨不留。
- `securityIds` 保留（显式清单直传通道，小清单场景 + 向后兼容）。
- 触发模式（rebalanceIntervalDays=0）不支持 pool → 400（沿用 industries 先例）。
