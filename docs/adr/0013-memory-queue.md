# 0013 — 长期记忆改为追加队列（FIFO + 队头折叠）

日期：2026-10-29
状态：已接受
关联：修订 ADR-0007（长期记忆部分）；会话内压缩见 ADR-0007 修订段与 `docs/历史对话滚动窗口改造方案.md`

## 背景

条目式长期记忆（ADR-0007：一条一文件、slug 唯一、update 原地覆盖）在真实使用中暴露三个缺陷：

1. **预算截断按 updated 降序（新者先留）**：老而重要的偏好会被后来的碎碎念静默挤出——"新近度=重要性"与实际相悖；
2. **语义重复拒收**：add 撞 slug 报错引导 update，导致"重新确认"这个最高频的记忆动作被迫走覆盖语义，无法体现频次；
3. **无复现刷新通道**：updated 只在显式 update 时刷新，对话中反复确认的内容没有任何机制维持其时效。

根因：把记忆当成"需要去重的文档集合"，而不是"随对话生长的流"。

## 决策

1. **存储**：一个用户一个 md 文件（`memories/<userId>/memory.md`），追加日志形态——frontmatter 持折叠摘要，
   正文为按追加序排列的记忆条目块；一条一文件与 slug 唯一性废弃。
2. **写入 = 追加，不判重**：新偏好、重新确认、修正统一为追加新条目（带时间戳与标题）；偏好变化也是
   追加修正版而非原地覆盖。「忘掉」物理删除未折叠匹配条目；已折叠部分以「已作废」条目声明，折叠时消化。
3. **容量触发队头折叠**：记忆区 token 估算（estTokens）超 `MEMORY_QUEUE_MAX_TOKENS`（缺省 2000）时，
   队头最老若干条并入记忆摘要（≤500 字），注入为队列头部；单轮击穿例外如实全量注入。
4. **注入**：`【用户长期记忆】`块 = 记忆摘要段 + 未折叠条目（追加序），每轮注入 system（含闲聊会话）；
   30 条/800 字旧预算与 `selectWithinBudget` 废弃。
5. **显式重要性标记（★/pinned）不做**：重要 = 用户会再提 → 追加即保活；频次就是重要性的度量。

## 理由

- **压缩次数 = 年龄，重要度随沉默衰减；频次 = 存活**：常提的记忆总会以新条目活在队尾，不再提起的
  随队头折叠慢慢淡化——衰减与保活由同一个追加机制统一实现，无需重要性评分或 touch 通道；
- **折叠兼去重**：多条语义重复的旧条目在队头折叠时被摘要器合并成一句，判重职责自然消解；
- **追加日志是唯一与三条机制同构的存储形态**：判重/覆盖语义与之根本冲突；
- 成本有界：记忆区恒 ≤ 队列预算（~1.5k tokens/轮），折叠单次 <1k tokens 且只在组装时 inline 发生。

## 后果

- `MemoryStoreService` 契约 breaking：`saveEntry/deleteEntry/listEntries` → `appendEntry/deleteMatching/readQueue`；
  旧 `<slug>.md` 一次性迁移导入队尾；
- `save_memory` 工具简化为 add（追加）/ delete（忘掉）两操作；[slug] 引用体系与撞车报错退役；
- 二次浓缩失真被接受：记忆本体即对话的二手浓缩，折叠摘要是有损层——原始对话仍在 messages 只追加日志；
- 语义重复在折叠前会并存注入（最多占满队列预算）——属显式接受的设计取舍。
