# 双数据引擎：字典即路由与来源无感

Status: accepted（2026-10-17 定案，待实施）

行业与板块数据（Tushare 下载）乃至将来的用户私密数据（如私密因子）需要独立于公共 MySQL 库（herms_data，只读账号）存取，且用户不应让 GLM 察觉私密数据的存在。决定：建本地文件引擎（DuckDB，单文件、支持直接读用户放入的 CSV、可物化 parquet）与公共库引擎并存；**数据字典物理分离**（公开 SQL/tables.md 与私密 SQL/private/ 各自维护），**取数按"字典即路由"**——表登记在哪个字典就从哪个引擎取，任何查询只打一个引擎；对模型呈现**合并后的统一数据目录**，不携带任何来源标记（来源无感：模型可点名"申万行业"或私密因子，但分不清其出处）。私密数据集注册时执行**注册保险**：表名/唯一键与既有表冲突硬拦，业务域重叠软告。私密数据文件与库文件不入 git，字典 md 入库。

## Considered Options

- **跨引擎合并查询 + 优先级去重**：否决——每个查询都要定义键对齐、列冲突的归属规则，SQL 层又脏又易错；在数据互补（而非竞争）的前提下，"一个查询只打一个引擎"的结构性消解优于任何冲突合并算法。
- **私密数据导入公共 MySQL**：否决——公共库账号只读，且私密数据进公共库本身就违背分离初衷。
- **数据集常驻内存**：否决——不可增量刷新、重启语义含糊、大文件不可扩展；文件库（DuckDB）保留 SQL 查询能力且与 MySQL 引擎对等。
- **内容无感（私密表对模型完全隐藏）**：否决——模型必须能点名数据（因子名、行业名）才能在对话中驱动回测，完全隐藏会使私密数据不可用；收敛为"来源无感"，泄露面仅剩数据集名字本身。
- **行业口径起点定池先行、PIT 二期**：否决（用户拍板一步到位）——申万成分 current+historical 两文件合并即可完整重建时点归属，边际成本低于一次返工。
