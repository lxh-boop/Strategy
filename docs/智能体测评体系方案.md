# 智能体测评体系方案

- 日期：2026-10-23
- 状态：**已拍板实施（ADR-0010）**——一期离线层当日落地：`evals/` 50 条任务 + harness/runner/指标卡全部就绪，冒烟通过；待拍板 6 问按推荐项执行（相对引用 / TS 用例 / judge 更高档可选 ZHIPU_JUDGE_MODEL / k=4 / reports 入 git / 在线层手动）。全量基线与在线层见下方"分期"。

## 1. 背景与目标

两个目的：

1. **对外指标卡**：非开发者一眼看懂"系统现在到什么水平"；
2. **优化依据**：改提示词、换 GLM 版本、加工具之后，有可比的指标变化曲线。

现成基准调研结论（2026-10-23）：BFCL / τ²-bench / SuperCLUE-Agent 测的是模型或通用智能体能力，InvestorBench / StockBench 测的是单标的交易决策，没有一个能测"因子研究智能体"的编排、参数口径、防编造、确认门。**结论是自建**，借鉴 τ²-bench 的 pass^k 方法论与任务模板形态。

## 2. 现状与不做的后果

现状：

- `factor-agent-server` 现有 283 个 jest 用例，全部是确定性断言：LLM 层 mock、外部依赖 mock。它们验证的是"**编排逻辑对不对**"，不是"**真实 GLM 驱动下表现多好**"。
- 真实 GLM 行为目前只有零散的真图冒烟（`test/core/implementations/langgraph-agent.service.spec.ts`）加人工试用，没有量化数据。
- `logs/`（backend / conversations / frontend 三类）和 `alphasage_user.messages.card` 沉淀了大量真实会话，但从未系统化抽取成用例。

不做的后果：

- 每次调提示词、升模型、加工具，只有"单测挂没挂"的二值信息；口径漂移、编造率变化这类已发生三次的真实风险，变化趋势无数据。
- 对外无法用数字说明水平。

## 3. 测评对象与两层用例

测评对象 = **LangGraph 智能体整体**（GLM + 提示词 + 工具定义 + confirm 节点），不是 GLM 模型本身。

| 层 | LLM | 工具/数据 | 测什么 | 特点 |
|---|---|---|---|---|
| 离线层 | 真 GLM | mock 桩（回测返回固定假结果、股票池返回固定集合） | 参数口径、编造、澄清、确认路由 | 快（分钟级一轮）、可反复跑 |
| 在线层 | 真 GLM | 真库真引擎端到端 | 任务完成率的最终形态（卡片与引擎回执一致） | 慢、依赖 MySQL/industry.duckdb，手动触发 |

与现有单测的关系是**分工不是替代**：mock-LLM 确定性单测继续守编排逻辑（免费、毫秒级、进 CI、必须全绿）；evals 用真实 GLM 测行为水平（慢、花 token、非确定，手动/定期跑，不进 CI 门禁）。

## 4. 指标定义（指标卡五项）

| 指标 | 口径 | 断言/评分方式 |
|---|---|---|
| 任务完成率 pass^4 | 同一任务独立跑 4 次**全部成功**才算通过（τ²-bench 口径）；成功 = 最终卡片/回执满足该任务声明的验收条件 | 硬断言（对 confirmedCalls 与回执字段） |
| 参数口径正确率 | 全部工具调用中关键参数与任务期望一致的占比；**断言点是 confirmedCalls 入参**（entryFilters / sortFactors / industries / weightFn / executionTiming / feeRate 等），不是回复文案——这是本领域"长引信"风险（引擎照跑、结果看似合理）的直接量化 | 硬断言 |
| 编造率 | 在诱导性任务集上（如"有色板块有哪些股票"，看起来能凭记忆答）不调用 `screen_stock_pool` / `read_factor_data` 而直接作答的比例 | 工具调用轨迹断言 |
| 澄清恰当率 | 双向计：该澄清没澄清（直接乱猜）+ 不该澄清乱问（啰嗦）；judge 模型按 rubric 打分，辅以人工抽检校准 | LLM-as-judge |
| 单任务成本 | 平均 LLM 轮数、工具调用次数、token 用量、墙钟时长 | 轨迹统计 |

指标卡形态：`reports/scorecard-<日期>.md` + 同名 `.json`（机器可对比），每跑一轮追加一份，趋势可见。

## 5. 目录设计（顶层 `evals/`，与前后端同级）

```
evals/
  README.md          # 方法论与口径说明（可直接对外引用）
  package.json       # 独立 TS 包；jest + ts-jest，与 server 同版本栈
  tsconfig.json
  src/
    harness.ts       # 装配真图：沿用 langgraph-agent.service.spec.ts 的 createTestingModule
                     #   装配方式，LLM 换真 GLM、工具换 mock 桩；采集完整轨迹
    runner.ts        # 跑批：按任务清单、每任务 k 次、顺序执行（尊重 GLM 并发限制）、
                     #   单任务失败隔离不中断整轮
    tasks-schema.ts  # 任务定义类型（id / 类别 / 用户输入 / 期望参数 / 验收条件 / 诱导标记）
    metrics.ts       # 指标计算（pass^k、口径正确率、编造率、成本）
    judges.ts        # judge 调用（澄清软项）
    report.ts        # 生成 scorecard md + json
  tasks/
    offline/         # 四组：口径 / 编造 / 澄清 / 确认路由
    online/          # 端到端真库任务
  prompts/           # judge rubric 提示词
  reports/           # 历次指标卡（建议入 git，可看趋势）
```

工程约束（现状：根目录无 npm workspaces，前后端各自独立 package.json）：

- evals 通过 tsconfig paths + jest moduleNameMapper 相对引用 `../factor-agent-server/src/**`。**不引入根 workspaces**——不做的后果是改动根 package.json 会动到前后端现有的安装与脚本习惯，影响面大；代价是 evals 的 tsconfig 必须与 server 保持一致（commonjs / ES2023 / experimentalDecorators），约束记入 evals/README。
- **server 侧零改动**：harness 只 import 不修改。若装配需要最小支撑（如某处需要放宽可见性或加注入点），单独提出来拍板，不在本方案里夹带。

## 6. 用例来源与一期数量（50 条起步）

| 组 | 数量 | 来源 |
|---|---|---|
| 参数口径 | 20 | `messages.card` 真实问法抽 10 条 + 构造变体 10 条（改日期 / 换行业 / 带 weightFn / 带 executionTiming）；期望参数按引擎语义人工标定 |
| 防编造 | 10 | 三次编造事故现场直接固化（含零工具调用编有色池那次）+ 变体；设计要点是问题"看起来能凭记忆答" |
| 澄清 | 10 | 缺日期 / 缺股票池 / 模糊指令（"帮我优化下策略"）等，含该问与不该问双向 |
| 确认路由 | 10 | approve 逐组放行、delegate 本轮全放行、feedback 回执三分类，含同批多回测逐组确认场景 |
| 在线 e2e | 5–8（不在 50 内） | 现有真库冒烟场景扩展：300750 分红换算、申万行业 PIT 选股、每日选股 weightFn 等 |

## 7. 分期

一期（拍板后）：

1. `evals/` 包骨架 + harness（复用真图装配）+ runner；
2. tasks-schema + 50 条用例标定；
3. metrics + scorecard 报表；
4. 跑通首轮基线，出第一张指标卡；
5. 随一期落 ADR（评测体系决策）与 GLOSSARY 词条（evals / pass^k / 指标卡）。

二期（看一期结果再定）：CI 手动触发入口、趋势曲线、用例扩到 100+、judge 校准与人工抽检流程。

## 8. 成本量级

离线层一轮 ≈ 50 任务 × 4 次 × 每次约 10–20 次 LLM 调用 ≈ 2000–4000 次调用，顺序跑约 20–60 分钟（受 GLM 并发限制）。在线层另计（真回测，每任务分钟级）。token 费用以 GLM 实际账单为准，首轮基线跑完把实际值记进指标卡。

## 9. 待拍板

2. **任务定义格式**：TS 文件（推荐，类型安全，参数期望结构复杂） vs yaml（非程序员可改）？
3. **judge 模型**：GLM 更高档位（推荐，judge 不与被评同档） vs 纯人工抽检？
4. **k 值**：4（推荐，τ²-bench 同款） vs 3（省 token）？
5. **reports 是否入 git**（推荐入，趋势可见；需确认轨迹快照无敏感信息）？
6. **在线层触发时机**：仅手动（推荐，一期不进 CI） vs 纳入定期任务？
