# 并发治理方案：GLM 调用协调器（信号量 + 限流退避重试 + 确认门限流保留 + 挂起恢复）

版本 v1.3（2026-10-29 修订：断点续跑改为「限流失败轮 thread 复用 + 简化组装」，模型驱动）
状态：待拍板（恢复语义已实测验证）
关联：ADR-0013（记忆队列）、docs/历史对话滚动窗口改造方案.md、`evals/records/`（限流观测来源）

## 一、背景与问题

后端与公司团队套餐共享同一智谱账户 key，限流窗口由全团队流量共同决定，外部饱和不可预测也不可制约。
据此只能制约自研代码——目标：让本服务成为团队套餐里最抗挤、最礼貌的客户端。

现状缺口（证据）：

1. **GLM 调用无任何协调**：`ChatOpenAI` 实例（langgraph-agent.service.ts:283）被 5 类调用点自由并发——
   agent 节点每轮对话（:324）、策略归因解读、历史折叠摘要、记忆折叠摘要、确认恢复（经 agent 节点）。
   跨会话并行闸 `inflightRuns`（:462）只拦同会话，跨会话/跨功能叠加全部放行。
2. **重试缺失**：ChatOpenAI 构造未设 `maxRetries`，底层 OpenAI SDK 默认仅 2 次 429/5xx 自动重试；
   团队级饱和窗口常超两次重试的跨度，429 穿透后**一整轮对话报废**（2026-10-28 日志实证 6 次）。
3. **确认门次生伤害**：resume 失败一律 fail-open「已退出确认模式」（langgraph:516）——限流这种可恢复错误
   把用户授权状态弄丢，需重新走确认。
4. **普通轮次限流失败无恢复**：工具已执行、模型分析轮限流失败 → 本轮终止，用户需重新描述问题
   才能接续（数据虽在 runs 表，但不是"直接回复就完成"）。

## 二、修正设计（全部只动自研代码）

### 2.1 GLM 调用统一入口 `withLlmSlot`（新增 ~45 行）

```text
withLlmSlot(fn):
  for attempt = 0.. :
    acquire 坑位（信号量，zhipu.maxConcurrency=2；满则排队等待）
    try   执行 fn
          成功 → 释放坑位 → 返回
    catch 429/限流：
          释放坑位（重试期间不占并发名额，不加压）
          attempt ≥ retryMax(10) → 抛出原错误
          退避 min(1s × 2^attempt, 8s) → 回到 for 重新排队
    catch 其他错误 → 释放坑位 → 原样抛出
```

- 限流判定 `isGlmRateLimitError`：错误消息含 `429`/`速率限制` 或匹配 /rate.?limit/i，
  兼容 `RateLimitCapacityError`、SDK 消息、LangChain 包装等多种形态；
- 退避序列 1s/2s/4s/8s/8s…（第 4 次起封顶 8s 不再增加），**重试上限 10 次**，
  总容忍窗口 ~63 秒——覆盖团队套餐的绝大多数瞬态饱和；
- **重试进度可见**（onRetry 回调）：agent 节点传入 onProgress 管道，每次退避推
  「GLM 限流，第 N/10 次重试（Xs 后）」进度事件 + 落日志——重试不再是黑盒；
  keepalive 心跳独立于重试循环持续喂，不触发前端 90s 看门狗；
  其他调用点（折叠/归因解读）无进度管道，只落日志；
- 5 个调用点统一包裹：`this.withLlmSlot(() => agent.invoke(...))` / `this.withLlmSlot(() => this.llm!.invoke(...))`。

### 2.2 确认门限流保留（修次生伤害，~10 行）

resume 失败的 fail-open 分支（langgraph:516）增加分流：

- **限流错误**（10 次重试仍失败）→ **保留 pendingConfirms 与检查点**，回复限流提示——
  用户稍后重发「确认」即可原地恢复，授权状态不丢；
- **其他错误** → 维持现状 fail-open（清挂起映射 + 弃检查点 + 退回普通对话）。

### 2.3 挂起恢复——限流失败轮的 thread 复用（核心，~20 行）

目标场景：一次问答中工具已执行完、模型分析轮（agent 节点 GLM 调用）限流失败且重试耗尽——
用户直接回复（说什么都行），模型看到已保存的现场与用户的新消息，**自行决定**接着完成任务。

**支撑事实（已在真实运行时实测，`.tmp_verify_resume.js` → 转正为单测）**：

1. 节点抛错后，检查点停在最后完成的节点：`messages=[.., AI(tool_calls), ToolMessage(回执)]`，
   `next=[失败节点]`——回执在场，断点即"工具刚完成"；
2. 同 thread 再次 invoke：从检查点恢复、只重执行未完成节点，已完成节点不重跑；
3. **带新消息 invoke：新消息并入检查点状态，图从入口节点重跑**——在我们的真实图
   （START → agent ↔ tools → END，agent 为入口）上，这意味着 agent 节点重新执行 =
   **重新调 GLM 做分析**（失败后本来就必须做的事），模型看到 `[..., AI(tool_calls),
   ToolMessage(回执), 用户新消息]`——回执与用户意图同时在上下文里，由 GLM 自行决定
   接着分析、按新要求调整、还是回应新问题；回执已在上下文，正常不会重复调工具。

**失败捕获**（runGraph catch 改造）：

- 限流错误 → **检查点保留** + `pendingResumes.set(conversation.id, threadId)` +
  回复："GLM 限流，进度已保存，直接回复即可继续"；
- 其他错误 → 维持现状（弃检查点，本轮终止）。

**下一问的 thread 复用与简化组装**（runGraph 开头，threadId 分配处分支）：

- `pendingResumes` 有挂起 → **threadId 复用挂起值**（不新建）；
  `prepareMessages` 走**续跑模式**：不重组 system/历史窗口（thread 检查点里上下文全在），
  只追加 `[HumanMessage(userText)]`——system/表目录/记忆块沿用首轮注入版本，无重复注入；
- invoke 正常携带 conversationId/userText/userId 通道（`roundsRun` 沿用挂起值，
  表目录撤除状态保持）；
- 模型看到完整现场自行处理：继续完成任务、按新消息调整、或回应新问题；
- collectReply → 完成：pendingResumes 清除 + 检查点收尾（沿用 B 规则：无挂起即删）；
- 恢复轮再遇限流耗尽 → 再登记挂起（同一 thread），可继续回复（用户驱动，无自动循环）；
- 恢复轮检查点失效（进程重启）→ invoke 报错 → 如实告知"断点已失效，请重新描述" + 清挂起。

**与 v1.2 的差异（为什么弃「继续」字符串匹配与 invoke(null)）**：

- 字符串匹配追不上自然语言（"继续吧""接着来"），且 GLM 被排除在决策外；
- `invoke(null)` 虽然严格"只重跑失败节点"，但用户消息进不了模型上下文；
- thread 复用 + 简化组装 = 让 GLM 看到回执与用户新消息自行处理——**入口节点重跑即重新分析**，
  无任何特殊恢复路径，实现最小。

### 2.4 配置旋钮

| `.env` 键 | 默认 | 含义 |
|---|---|---|
| `GLM_MAX_CONCURRENCY` | 2 | 本进程在飞的 GLM 调用上限（超出排队） |
| `GLM_RETRY_MAX` | 10 | 429 退避重试次数上限（退避封顶 8s） |

## 三、不做什么

- **不立 ADR**：可回退的工程修复，不满足"难回退 + 令人惊讶 + 真实取舍"门槛；
- **不做跨进程协调**：单进程部署形态，互斥/信号量进程内有效即可；
- **不改 HttpZhipuService**：对话链路走 LangChain ChatOpenAI，重试与限流在调用协调层统一处理；
  `HttpZhipuService` 当前无调用方，保持原样；
- **非限流失败不进挂起恢复**：超时/参数错误等维持现状（弃检查点），观察一段时间再评估扩大。

向团队申请为本服务单独的 API key 或子账号配额。全团队共享 key 的架构下，任何客户端优化
只能降低撞车概率与自动恢复，不能根治。

## 五、验证

1. **单测**：`isGlmRateLimitError` 形态覆盖；`withLlmSlot` 并发上限（模拟在飞计数）、429 重试后成功、
   重试耗尽抛出；确认门限流保留（挂起映射不删）；挂起恢复（限流耗尽 → 检查点保留 + 登记 →
   下一问复用同 thread + 简化组装断言：stub 收到的消息仅含新 HumanMessage、含上一轮回执；
   恢复轮再限流 → 再挂起；挂起期间发消息后正常收尾清挂起）；
2. **回归**：server 全量 jest（stub agent 经 withLlmSlot，默认参数无干扰）；
3. **真实观测**：日志出现「GLM 限流退避」行且最终成功（回执正常）；「已退出确认模式」不再因 429 出现；
   限流耗尽后直接回复，日志可见同 thread 续跑且回测零重跑（回测次数不变）。

## 七、重试耗尽后的失败处理语义

重试 10 次（~63 秒退避窗口）仍 429 → 说明饱和是持续性的，**不再自动重试**（自动重启图执行只会
循环加压），本轮以错误回复收尾。分场景：

| 场景 | 失败点 | 处理 | 数据损失 |
|---|---|---|---|
| 普通轮次（工具已执行） | agent 节点分析轮 | **检查点保留进 pendingResumes**，回复："GLM 限流，进度已保存，直接回复即可继续"；下一问复用同 thread + 简化组装，GLM 带现场自行完成 | 无——回执/卡片/card_N 在工具执行完即落 runs 表 |
| 确认门挂起中 | resume 的模型调用 | 确认态与检查点**保留**，稍后重发「确认」原地 resume | 无 |
| 历史/记忆折叠 | 折叠摘要调用 | 宁多勿失：本轮全量注入，下次组装重试折叠 | 无 |
| 归因解读 | 解读调用 | 既有口径"解读失败不挡数据层"，聚合数据照常返回 | 无 |

关键事实：**失败的是"模型分析"这一步，数据层面零损失**——工具执行完即已落袋（回执进
ToolMessage、卡片进图状态、card_N 落 runs 表）。检查点恰好停在"工具刚完成"的断点上，
配合 thread 复用与简化组装，用户直接回复即可让 GLM 带着现场完成剩余工作。
