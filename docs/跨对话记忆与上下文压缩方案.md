# 跨对话记忆与上下文压缩方案（长期记忆 + save_memory + 滚动摘要）

日期：2026-10-21　状态：已实施（五刀当日完工，未提交；industry-engine 套件因运行中的后端锁 industry.duckdb 暂不可跑，与本次改动无关）
配套：GLOSSARY「记忆」词条、ADR-0007

## 一、背景与问题

现状记忆边界三层，全部硬截断、零压缩机制：

1. **轮内完整**：LangGraph 循环内工具调用与回执当轮可见。
2. **轮间只剩 3 轮文字**：`prepareMessages` 取 `conversation.messages.slice(-6)`（`langgraph-agent.service.ts:1064`），每轮落库 1 用户 + 1 回复（`conversations.service.impl.ts:89`）；卡片（`m.card`）与工具回执从不进 prompt，模型只记得自己气泡里写过的文字。
3. **跨对话为零**：新会话只有 system prompt + 欢迎语，上周调好的策略、说过的偏好全部不可知。

后果：调优对话超过 3 轮即失忆（"把第一个因子去掉"里的"第一个"可能已滑出窗口）；换会话必须从零重新描述偏好与结论。压缩机制（写入压缩/库内合并/会话内摘要）代码里均不存在。

机制参照 DeepSeek Harness compaction 公开资料：长度触发、摘要替换一段模型可见历史、**原始日志永不覆盖**（模型可见历史必须能从日志完整重建）——本项目 MySQL `messages` 表即现成的只追加日志（`mysql-user-store.service.ts:270` appendMessages），摘要可随时从原文重炼、无"摘要的摘要"层层失真。

## 二、决策记录（grill 三轮收口，2026-10-21）

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 记什么 | 条目式记忆：用户画像/偏好 + 策略研究记忆；不存全量会话摘要 |
| 2 | 存哪 | **本地 md 文件，零数据库**（用户明确否决 MySQL）；`memories/<userId>/` 一人一目录，一条记忆一个 md 文件 |
| 3 | 怎么写 | GLM `save_memory` 三操作工具（新增/更新/删除）+ 用户显式指令；**不过确认门**；写入回执必须在回复中可见 |
| 4 | 怎么读 | 每轮全量注入 system prompt，预算封顶（缺省 ≤30 条或 800 字，先到为准，按 updated 降序淘汰最旧） |
| 5 | 库内压缩 | 写入现场由模型完成：模型每轮见全量条目，改偏好 = 现场 update 覆盖，无后台合并任务 |
| 6 | 会话内压缩 | **长度触发**（气泡总字符数，非条数）；超阈值把尾部之外的全部原文重炼成**一条摘要消息**注入；保留近段原文；后台异步 |
| 7 | 数值 | 触发 2000 字 / 尾部 800 字 / 摘要 ≤400 字 / 单会话原文 >3 万字退化"旧摘要+增量"重炼；全部配置旋钮 |
| 8 | 原始记录 | 永不覆盖：摘要 = 派生缓存（md 文件），删了可从 messages 原文重建 |
| 9 | 管理 | v1 无 UI：对话指令（"记住/忘掉"）+ 直接手改 md 文件，双通道 |

与既有原则的划界：**记忆属用户上下文，任何会话（含闲聊）都注入**；"数据会话·闲聊零注入"（GLOSSARY）只管数据上下文（表目录、轮次预算），两者不冲突，已在 GLOSSARY 写明。

## 三、设计

### 3.1 长期记忆条目（存储层）

- 新抽象契约 `MemoryStoreService`（core 层，SVC-D24），唯一实现 `memory-file-store.service.ts`。
  **不做** UserStoreService 式 memory 兜底双实现——文件天生本地可用，测试注入 tmp 目录即可。
- 目录：`${MEMORIES_DIR:-<运行目录>/memories}/<userId>/<slug>.md`；`memories/` 进 `.gitignore`。
- 条目文件 = frontmatter（`title` / `created` / `updated`）+ 正文（1~3 句话事实，一条一事）。slug 由模型供给、后端清洗为 `[a-z0-9-]`，中文标题放 `title`。
- 注入读法同表目录先例（`factor-schema.ts:22`）：目录扫描全读、现读现拼（微秒级），超预算按 updated 降序截断。

### 3.2 save_memory 工具（写入侧 = 库内压缩）

- `tool-specs.ts` 加 `SAVE_MEMORY_SPEC` + 入 `AGENT_TOOL_SPECS`（`:508`），agent 侧一行注册（`:567` 惯例："新增工具 = 一条 schema + 一行注册，不动图结构"）。
- schema：`op: add|update|delete`；`slug`（update/delete 必填且必须已存在，否则回执报错）；`title`、`content`（add/update 必填）。
- 回执文案：`已记住：<title>` / `已更新：<title>` / `已忘掉：<title>`；`toolEventDetail`（`:1044`）加一行，进度流可见。
- **可见性即防线**：本项目编造事故三次，记忆又是持久态——v1 不设确认门（用户拍板），但每次写入必须双通道留痕（进度事件 + 模型气泡复述），错记可经对话指令或手改文件清除。

### 3.3 记忆注入（读取侧）

- `buildSystemPrompt`（`:1078`）加记忆段，位置：工具流程之后、表目录之前（表目录仍居最末）。
- **userId 贯通**（现状 `Conversation` 不带 userId，`types.ts:278`；`reply(conversation, userText, routeText)` 签名亦无，`agent.service.ts:20`）：`prepare`（`conversations.service.impl.ts:78`）把 userId 附加到传给 agent 的会话对象，随 `Conversation` 可选字段贯通到 `buildSystemPrompt` / `prepareMessages`。

### 3.4 会话滚动摘要（上下文压缩，长度制）

`prepareMessages` 的 `slice(-6)` 退役，改注入形态：

```
┌ SystemMessage：system prompt（含记忆段）
├ SystemMessage「[历史对话摘要] …」     ← coveredChars 之前全部原文的重炼，≤400 字；仅当存在
├ 压缩点之后的消息原文（逐条）          ← 上次压缩后的新消息，800~2000 字
└ HumanMessage：本轮输入
```

- **度量**：气泡文本总字符数（不引 tokenizer，确定性）。
- **无损不变式**：任何历史消息要么在摘要里、要么原文注入，二选一必居其一。压缩时保留末尾约 800 字原文（`coveredChars = 总字数 − 尾部字数`），此后新消息不覆盖、原文注入。
- **触发与再炼**：回复完成后检查，未覆盖部分超过滞后带（TRIGGER − TAIL = 1200 字）→ 后台异步重炼（不挡响应）；懒兜底：`prepareMessages` 发现落后且后台未完成 → 当轮内联重炼（一次性延迟，罕见路径）。
- **重炼取材**：永远从 `conv.messages` 全量原文取材（含旧摘要覆盖部分），无失真累积；原文 >3 万字退化为「旧摘要 + 增量消息」重炼，防摘要调用 prompt 无界。
- **缓存**：`memories/<userId>/_threads/<conversationId>.md`，frontmatter 记 `coveredChars` / `updated`；丢了可重建，会话删除/清空挂钩清理。
- 短会话（未超触发阈值）全量原文注入，保真度优于现状的 6 条硬截断。

### 3.5 生命周期

- `deleteConversation` / `clearConversation`（`conversations.service.impl.ts:34/40`）挂钩清摘要文件。clear 必须清（否则摘要提及已删消息）；**长期记忆条目不随会话删**——它是跨对话本体。
- 多用户靠 `<userId>` 目录天然隔离；单人部署无害。

### 3.6 配置

| 配置 | 缺省 | 含义 |
|------|------|------|
| `MEMORIES_DIR` | `<运行目录>/memories` | 记忆文件根目录 |
| `MEMORY_TRIGGER_CHARS` | 2000 | 触发压缩的历史总字数 |
| `MEMORY_TAIL_CHARS` | 800 | 压缩时保留的近段原文字数 |
| `MEMORY_SUMMARY_CHARS` | 400 | 摘要目标上限 |
| `MEMORY_MAX_ENTRIES` | 30 | 注入条数上限 |
| `MEMORY_BUDGET_CHARS` | 800 | 注入字数上限（与条数先到为准） |

## 四、功能清单（验收口径）

- **F1 存储层**：`MemoryStoreService` 契约 + 文件实现。增/改/删/列/预算截断；slug 清洗非法字符；损坏条目（坏 frontmatter）跳过不炸；tmp 目录单测。
- **F2 写入闭环**：save_memory 工具注册进图；三操作全通；update/delete 引用不存在 slug 时回执报错而非静默；回执双通道可见。
- **F3 记忆注入**：记忆段进 system prompt 且闲聊会话也注入；条数/字数预算截断生效；记忆为空时 prompt 与现状完全一致（行为兼容）。
- **F4 滚动摘要**：短会话全量注入（slice(-6) 行为消失）；超阈值触发后台压缩；无损不变式成立（可写性质测试：任意消息序列下，注入内容 ⊇ 摘要 ∪ 压缩点后原文）；懒兜底路径可用；SystemMessage 注入带前缀、不伪造对话轮次。
- **F5 生命周期**：删会话/清会话 → 摘要文件清理；长期记忆条目不受影响。
- **F6 退役**：`slice(-6)` 移除；既有 agent 测试全量回归（146 基线 + keepalive-gate）。

## 七、风险与已知边界

- **摘要有损**（用户知情确认）：窗口外细节只留摘要写下的部分；原文在库，可随时人工核查或重炼。
- **记忆无门**（用户拍板）：持久态写入无确认门，防线 = 回执双通道留痕 + 对话删除 + 手改文件；若出现记忆被写歪的事故，再议审计列表/软删除。
- **每轮注入增量**：记忆段 ≤800 字 + 摘要 ≤400 字，闲聊会话也承担；换来跨对话能力，预算旋钮可收紧。
- **后台摘要的 API 费用**：超阈值会话每轮多一次 flash 级摘要调用（小 prompt）；滞后带保证频率有上界。
