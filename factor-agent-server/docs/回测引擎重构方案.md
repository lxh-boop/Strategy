# 回测引擎全面重构方案

> 版本 v3（2026-10-12）· 状态：**已实施**（分支：回测，同日完成）
> 评审人：chenhaotao · 预期排期：3 天（确认后开工）
> v2 变更：因子按引擎视角二分类（筛选类/可排序类，数据源对引擎不可见）；阶段合并为两项；参数寻优职责定死归 GLM 编排层
> v3 变更：删除 FactorDef 抽象；因子全部读库（引擎不在线计算）；过滤/排序拆为两个独立参数（同一因子两处重复传入）；默认动量因子方向定死值大优；排序方向与默认因子须在确认弹窗展示；排序因子保留可选 weight（缺省等权 1/N）
> 实施差异见 §14 实施记录（securityIds 形态、换手口径、静态表处理、脏数据防御等）

---

## 1. 背景与目标

### 1.1 现状

现有回测引擎为**净值制截面引擎**：每个调仓期对全市场因子做分位数等权合成，按综合分取 Top-K 等权持有，输出净值曲线与区间指标。该引擎支撑了 TOOL-C07 多因子等权回测链路（含确认门、授权调优、前端弹窗）。

### 1.2 能力缺口（重构动因）

本轮"商品涨价传导策略"暴露三类无法在现引擎上表达的语义：

| 缺口 | 说明 |
|---|---|
| 日频风控信号 | "个股跌破 MA20 当日卖出"是持仓期内的日频事件，截面引擎只在调仓日行动 |
| 资金管理 | 初始资金 100 万、整手（100 股）约束、单只仓位上限——净值制引擎无现金/持仓概念 |
| 策略多样性 | 主题择时、条件触发等策略形态需要一个**参数驱动**的通用执行框架，而非逐个硬编码 |

### 1.3 目标

**全面重构**回测引擎为**日频事件驱动内核**，同时满足：

1. 过滤/排序分参：两个独立参数传入引擎，同一因子既过滤又排序时两处重复传入
2. 信号与执行分离：T 日收盘算信号，T+1 执行——无未来函数
3. A 股规则内建：T+1 持有制度、整手、停牌顺延、费用逐笔
4. GLM 编排：内核只收数字参数，语义翻译全部在 GLM 工具调用层
5. 确认门弹窗（已建）原样接入

### 1.4 明确不做（本期边界）

- 实盘级撮合（队列/逐笔撮合模拟）
- 滑点模型（参数预留，一期不启用——用户已定不设滑点）
- 分钟级数据回测（数据源无分钟级，已核实）
- 参数自动寻优（**GLM 编排层职责**：授权调优流程串行多组对比 + 汇总择优已覆盖；引擎只执行单次给定参数的回测，任何形式的参数网格/自动寻优都不进引擎）

## 2. 设计原则（已与需求方确认的四条）

1. **全面重构，不做增量**——原引擎架构无法表达新语义，推倒重来
2. **GLM 对话即语义层**——文本到数字的翻译全部发生在 GLM 工具调用（编排层），内核只收数字，零文本零语义
3. **过滤/排序分参 + 默认兜底**——过滤与排序是两个独立参数（同一因子既过滤又排序时两处重复传入）；sortFactors 为空时自动追加 20 日动量（方向定死值大优）为默认排序因子，并在确认弹窗中告知用户
4. **引擎全面性**——日频事件循环、T+1、资金账户、整手约束完整实现，不做"月度截面简化"
5. **职责边界**——引擎只执行单次给定参数的回测；多组参数的寻优、编排与对比择优是 GLM 编排层（授权调优流程）的职责，引擎永远不做参数自动寻优（策略可以简化，引擎不行）

---

## 3. 总体架构

```
用户（自然语言对话）
   ↓ ① 意图理解 + 因子发现 + 参数限定
GLM 编排层（TOOL-C04/05 查字典 → 因子取值限定 → 组装数字参数）
   ↓ ② TOOL 调用：run_strategy_backtest(params)   ← params 全数字 + 字段引用
确认门（interrupt 暂停 → 前端弹窗：确认执行/授权调优/输入其他要求）
   ↓ ③ resume（精确匹配："确认"/"授权调优"，零模糊）
回测内核（日频事件循环，纯数字）
   ↓ 净值序列 / 交易明细 / 区间指标
回测卡片渲染 + 汇总对比择优
```

**分层纪律**（定死）：

| 层 | 职责 | 禁止 |
|---|---|---|
| 前端对话 | 自然语言、弹窗按钮 | 不传任何语义文本给内核 |
| GLM 编排 | 意图→数字参数、因子发现 | 不做数值模拟计算 |
| 回测内核 | 纯数字模拟 | 不解析任何策略名/语义文本 |

## 4. 数字内核参数接口（StrategySpec v1）

```ts
interface BacktestParams {
  // ── 股票池（前置筛选工具产出的证券内部 ID 列表）──
  securityIds: number[];

  // ── 区间与资金 ──
  startDate: number;          // YYYYMMDD
  endDate: number;            // YYYYMMDD
  initialCapital: number;     // 初始资金，默认 1000000
  feeRate: number;            // 单边费率，默认 0.0003

  // ── 调仓 ──
  rebalanceIntervalDays: number;  // 每 N 个交易日调仓
  executionTiming: 0 | 1;         // 0=开盘价成交 1=收盘价成交

  // ── 持仓 ──
  maxPositions: number;           // 最大持仓数，默认 10
  idealPositionPct: number;       // 每只理想仓位 %，默认 10
  minPositionPct: number;         // 最小建仓仓位 %，默认 1

  // ── 过滤因子（全部满足才入选；与排序分开传，GLM 从字典发现并填）──
  entryFilters: FilterRule[];

  // ── 排序因子（分位加权合成，缺省等权；与过滤分开传，确认弹窗须展示方向与权重）──
  sortFactors: SortFactor[];

  // ── 卖出规则（持仓期每日检查，GLM 填）──
  sellRules: SellRule[];
}

// 过滤因子：按 table.field 从数据表读值，不满足即剔除
type FilterRule = { table: string; field: string; op: '>' | '<'; value: number };

// 排序因子：direction 1=值大优（降序）/ -1=值小优（升序），默认因子方向定死 1；
// weight 缺省不传 = 等权 1/N；需要加权时 GLM 给全部排序因子传 weight，引擎按总和归一化
type SortFactor = { table: string; field: string; direction: 1 | -1; weight?: number };

type SellRule =
  | { kind: 'field'; table: string; field: string; op: '>' | '<'; value: number }  // 字段条件触发（如收盘<MA20 的标记字段）
  | { kind: 'stop_profit'; pct: number }
  | { kind: 'stop_loss';   pct: number }
  | { kind: 'max_drawdown_from_entry'; pct: number }
  | { kind: 'max_hold_days'; days: number }
  | { kind: 'rank_out'; bottomN: number };
```

**说明**：

- 一期引擎不计算任何因子：所有因子值一律按 table.field 从数据表读取（K 线因子表、财务表等白名单内表）
- 同一因子既过滤又排序（如"收益率>5% 且按收益率排序"）→ 在 entryFilters 与 sortFactors 各传一次，引擎不合并
- weight：全省略 = 等权 1/N；加权模式下 GLM 必须给全部排序因子传 weight（引擎按总和归一化），不支持只传部分
- `securityIds` 由前置筛选产出：GLM 可先调筛选工具（行业成分/财务过滤）得到清单，也可传入静态清单

## 5. 内核执行循环

```
预取阶段（回测开始前一次性完成）
  全股票池日行情（前复权 OHLCV+成交额，用于成交与结算）、基准指数行情、各因子历史截面（按 entryFilters/sortFactors/sellRules 引用的 table.field 预取）

主循环（逐交易日 D）：
  ── 执行阶段 ──
  执行昨日盘后生成的指令：
    调仓指令 → 以 D 日开盘价调仓到目标持仓（整手取整、费用扣现金）
    卖出指令 → 卖出指定持仓，资金回现金
  ── 结算阶段 ──
  权益 = 现金 + Σ(持仓股数 × D 日收盘价)；记录当日净值/持仓快照
  ── 信号阶段（D 日收盘后）──
  读取全部因子截面值（预取数据，不在线计算）
  若 D 为调仓日：按过滤+排序生成目标持仓 → 生成 D+1 调仓指令
  逐持仓检查卖出规则 → 生成 D+1 卖出指令
```

### 执行纪律（A 股规则内建）

| 规则 | 引擎实现 |
|---|---|
| 信号与执行分离 | 信号用 T 日收盘数据，T+1 开盘价执行 |
| A 股 T+1 制度 | 当日买入标记 `buyDate`，当日不可卖 |
| 卖出资金 | 当日可用于买入 |
| 停牌 | 无成交价：跳过该标的交易，持仓顺延 |
| 涨跌停（一期简化） | 触及涨跌停价的委托视为不可成交，顺延至可成交日 |

### 资金账户

| 规则 | 实现 |
|---|---|
| 初始资金 | 100 万（可配） |
| 买入 | 目标市值 → 整手股数向下取整 → 万三费用扣现金 |
| 卖出 | 全部持仓卖出，费用扣减，资金回现金 |
| 现金不足 | 按可用资金缩股；仍不足 → 顺延下一候选 |
| 空闲资金 | 一期留存现金（不配置货基） |

## 6. 因子层

### 6.1 因子即取数规格（不做 FactorDef 抽象）

引擎内没有"因子对象"：过滤和排序是两个独立参数（§4 entryFilters / sortFactors），每条就是 { table, field } 取数规格加数字阈值/方向。

- 因子可用范围 = SQL/ 白名单字典内的表.字段；引擎不解析语义，只按引用取数
- 一期引擎不计算任何因子（MA/动量/量能等一律不做在线计算），全部读库
- 同一因子在两个参数中重复传入时不合并——过滤与排序本就是两次独立使用

### 6.2 调仓日处理流水线（定稿）

```
① 全股票池按 entryFilters / sortFactors 的 table.field 读取因子截面值（预取数据，不在线计算）
② 过滤：entryFilters 逐条检查，不满足即剔除
③ sortFactors 为空 → 追加默认排序因子（20 日动量·值大优）
④ 存活股票：各排序因子截面分位数标准化（0~100）→ 加权平均（缺省等权 1/N）→ 综合分
⑤ 综合分降序取前 maxPositions → 等权目标持仓
⑥ 通过过滤的不足 maxPositions → 有多少持多少，现金留存
```

### 6.3 默认排序因子（sortFactors 为空时自动追加）

- 20 日动量（K 线因子表对应字段，字段名开工时对库确认），direction 定死 **1（值大优：涨得多优先）**，不提供反转配置
- 用户传入 sortFactors 时，默认因子不追加
- GLM 组装参数时即把默认因子显式写入 sortFactors（确认弹窗自然可见）；引擎保留 sortFactors 为空时的兜底追加，双保险

### 6.4 因子的两个参数（进入引擎即分开）

引擎不关心因子的业务含义；过滤与排序在参数层就是两个独立列表，不共用定义：

| 参数 | 结构 | 语义 |
|---|---|---|
| entryFilters | { table, field, op（'>' / '<'），value } | 不满足 → 剔除，不进入持仓 |
| sortFactors | { table, field, direction（1=值大优 / -1=值小优），weight?（缺省等权） } | 截面分位数标准化 → 加权合成综合分（缺省等权）→ 降序取前 maxPositions |

全部因子值一律从白名单内的数据表读取（K 线因子表、财务表、行业表、主表状态字段等），引擎不做在线计算；上穿/下穿类事件条件由库中预计算的标记/状态字段表达。

## 7. GLM 编排层

### 7.1 职责（语义→数字的唯一翻译点）

| 步骤 | GLM 做什么 | 工具 |
|---|---|---|
| 因子发现 | 用户说"商品涨价传导" → 查表目录/字段字典，确定可用因子与字段 | TOOL-C04/05 |
| 股票池筛选 | 按行业/财务条件筛出 securityIds | 筛选工具 |
| 参数限定 | 把"2025年、月调仓、top10、万三费用"翻译为数字参数 | 意图理解 + 今日日期注入 |
| 确认门 | 组装 params 调用回测工具 → interrupt → 前端弹窗 | run_strategy_backtest |
| 多组对比 | "授权调优"后连续调用（不同参数），汇总对比择优 | 串行编排 |

### 7.2 提示词（已并入回复规则）

- 回测区间只能来自用户说过的'时间，禁止凭经验填日期（已建）
- 优化建议结尾固定加：回复"授权调优"可按建议连续多组回测对比择优（已建）
- 新增：给出策略参数提案时，参数以结构化清单展示给用户确认（已建，弹窗）

## 8. 确认门与前端（已上线组件的接入）

| 组件 | 状态 | 接入 |
|---|---|---|
| 参数确认弹窗 | ✓ 已上线 | interrupt 暂停 → 弹窗（参数瓦片 + 确认执行/授权调优/输入行）→ 精确匹配 resume |
| 优化建议弹窗 | ✓ 已上线 | 优化建议回复自动弹出（按建议执行/授权调优·连续对比/输入行） |
| 停止按钮 | ✓ | 授权调优多组执行中可中断 |

确认/授权的决策匹配为**精确匹配定死**（"确认"→approve；"授权调优"→delegate；其余 → feedback 交模型），正则模糊匹配已删除。

**弹窗展示要求（v3 新增）**：参数确认弹窗必须完整展示排序因子清单及各自方向（值大优/值小优）与权重（等权或具体百分比）；sortFactors 为空时，GLM 组装参数即显式写入默认 20 日动量因子（值大优），弹窗如实展示——排序方向、权重与兜底行为对用户透明。

### 14.2 与方案的差异（实施时确定）

1. **securityIds 形态**：`string[]`（SECURITY_ID 形态 `000002.XSHE`）而非内部 ID `number[]`——GLM 从字典/筛选工具拿到的是证券代码，内部 ID 对语义层不可读；空数组/缺省 = 全市场。上限 5000。
2. **默认动量因子对库确认**：`equ_factor_obos.REVS20`（字典口径"20日价格动量：过去 20 个交易日区间收益率"）。
3. **换手率口径**：年化单边换手 = Σ(当日买卖双边交易额)/2 ÷ Σ(日权益) × (252/天数) × 100；卡片与摘要同源。
4. **静态表支持**：无 TRADE_DATE 列的主表（md_security 等 5 张）作 entryFilters/sellRules 引用时，截面/序列查询忽略日期条件（值与日期无关）——退市状态过滤等场景可用。
5. **rank_out 生效时点**：仅在调仓日（按当日综合分排名判定，跌出 bottomN 或被过滤剔除即卖出）；非调仓日不检查（不预取每日全池截面）。
6. **脏数据防御**：行情装载时 close/preClose 非正数的行丢弃（等同停牌）、open 非正数置 null（该日不可开盘成交）；买入股数加有限性校验——真库验证发现开盘价 0 的脏行会把 NaN 顺着资金账户扩散（600543@20240705），已在装载入口拦截。
7. **容量护栏**：调仓间隔 1~250 个交易日；调仓次数上限 550（约两年日频）；候选股票并集上限 1500（超过报错提示降频/减仓/缩区间）——控制全市场场景的截面查询量与行情内存面板。
8. **T+1 简化**：持仓按"最近买入日"整仓锁定（不做按批次 lots）；补仓当日旧仓也顺延一天可卖，影响 ≤1 个交易日。
9. **涨跌停一期口径**：统一 ±10%（执行价相对昨收 9.99% 阈值），ST 5%/创业科创板 20% 档不做区分（方案 §11-5 已定一期简化）。
10. **交易明细输出**：卡片截最近 50 笔（方向/价格/股数/金额/费用/触发原因），全量在引擎内存中（未落 backtest_runs 表，独立存储方案另行拍板）。
