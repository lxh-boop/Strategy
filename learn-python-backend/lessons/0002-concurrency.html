必考八股

必考

GIL 是什么？为什么要有它？它影响哪些场景？

考察点

GIL 的作用、代价和边界；能用数据说明"CPU 密集多线程不加速"。

30 秒回答

GIL（全局解释器锁）是 CPython 里的一把全局锁，保证同一时刻只有一个线程在执行 Python 字节码。好处是让 CPython 的对象模型（尤其是引用计数）天然不怕多线程并发修改，实现简单。代价是：默认版本的 CPython 里，多个线程跑 CPU 密集的 Python 代码无法利用多核并行。但官方文档说得很清楚，做 I/O 时 GIL 一定会释放，所以 I/O 密集的程序用多线程依然有效；一些 C 扩展（比如做压缩、哈希的模块）在重计算时也会主动释放 GIL。

1 分钟复现（3.12 实测，存成文件运行）

import time, threading
from concurrent.futures import ProcessPoolExecutor
def work(_=None):
    n = 0
    for _ in range(40_000_000):
        n += 1

if __name__ == '__main__':          # Windows 上多进程必须有这行保护
    t = time.perf_counter(); work(); work()
    print('串行', round(time.perf_counter() - t, 2))       # 3.12 秒
    t = time.perf_counter()
    ts = [threading.Thread(target=work) for _ in range(2)]
    for x in ts: x.start()
    for x in ts: x.join()
    print('两个线程', round(time.perf_counter() - t, 2))   # 2.90 秒 —— 没有加速
    t = time.perf_counter()
    with ProcessPoolExecutor(2) as ex: list(ex.map(work, range(2)))
    print('两个进程', round(time.perf_counter() - t, 2))   # 1.85 秒 —— 真并行（含进程启动开销）
为什么不干脆去掉 GIL？
已经在做了：官方有不带 GIL 的自由线程版本（见本课第 10 题）。去掉 GIL 要给引用计数等内部机制重新做线程安全，单线程性能有损失，C 扩展也要适配，所以目前还不是默认版本。
有 GIL 是不是就不用加锁了？
不是，见第 6 题。

常见错误

说"Python 多线程没用"——I/O 密集照样有用；或说"GIL 让 Python 代码线程安全"——它只保证单条字节码不被打断。

必考

多线程、多进程、协程分别适合什么场景？怎么选？

30 秒回答

看任务类型。CPU 密集（纯 Python 计算）：用多进程绕开 GIL，或者把计算交给会释放 GIL 的 C 扩展。I/O 密集、并发量不大（几十个请求、调几个接口）：线程池最简单，现成的同步库直接能用。I/O 密集、并发量很大（成千上万的连接、WebSocket、爬虫）：用 asyncio，单线程靠事件循环切换，开销远小于线程，但要求整条链路都用异步库。混合场景：asyncio 做主体，CPU 重的部分交给进程池。

多进程多线程协程（asyncio）
能否用多核能默认版本不能（GIL）不能（单线程）
适合CPU 密集I/O 密集、中等并发I/O 密集、海量并发
何时切换操作系统调度操作系统抢占式调度只在 await 处主动让出
开销最大：独立内存，数据要序列化中：每个线程一个栈最小
主要的坑进程间通信、启动慢竞态，要加锁一处阻塞，全部卡住
和 Node 对比？
Node 就是单线程事件循环（对应 asyncio），CPU 重活交给 worker_threads 或多进程（cluster）——思路和 Python 一致。区别是 Node 生态天生异步，Python 要自己挑异步库，混进一个同步库就可能卡住整个循环。
必考

asyncio 是怎么工作的？

30 秒回答

asyncio 是标准库里的异步 I/O 框架，核心是事件循环：一个线程里跑一个循环，不断检查"哪些任务等待的 I/O 已经就绪"，就恢复执行那个任务。协程用 async def 定义，执行到 await（比如等网络响应）时主动把控制权交还给事件循环，循环趁这段时间去跑别的协程，I/O 完成后再回来接着执行。所以单线程也能同时处理成千上万个连接——前提是每个协程都在该等的时候 await，不霸占循环。这和 Node 的事件循环模型几乎一样，程序入口通常是 asyncio.run(main())。

和 Node 最大的区别是什么？
两点：一是 Node 生态天生异步，Python 有大量同步库（requests、pymysql），在协程里误用就会卡住循环（见第 4 题）；二是调用 async 函数时的行为不同，见进阶第 12 题。

加分项

uvloop：用 Cython 写在 libuv 之上的 asyncio 事件循环替代品（libuv 正是 Node 底层用的那个库），官方 README 称能让 asyncio 快 2–4 倍，uvicorn 这类服务器装上就能用。

必考

在 async 函数里调用了同步阻塞的代码，会发生什么？怎么解决？

考察点

异步编程第一大坑。答出"整个事件循环被卡住"和至少两种解法。

30 秒回答

整个事件循环会被卡住。事件循环是单线程的，只在 await 处才能切换任务；如果在 async 函数里调用了同步阻塞的代码（time.sleep、requests.get、同步数据库驱动、大段 CPU 计算），这段时间里循环上的所有任务都停摆，一个慢请求拖慢所有请求。官方文档明确说阻塞代码不应该在协程里直接调用。解法：换成异步库（httpx 或 aiohttp、asyncpg 或 aiomysql、asyncio.sleep）；实在要调同步代码，用 asyncio.to_thread(func) 或 loop.run_in_executor 放到线程池里跑；CPU 密集的放进程池。

1 分钟复现（3.12 实测）

import asyncio, time
async def ticker(t0):
    for i in range(3):
        print('tick', i, round(time.perf_counter() - t0, 1))
        await asyncio.sleep(0.5)
async def bad():  time.sleep(1.5)                           # 同步阻塞
async def good(): await asyncio.to_thread(time.sleep, 1.5)  # 放到线程里
async def main(job):
    await asyncio.gather(ticker(time.perf_counter()), job())

asyncio.run(main(bad))    # tick 0 0.0 / tick 1 1.5 / tick 2 2.0 —— 中间被卡了 1 秒
asyncio.run(main(good))   # tick 0 0.0 / tick 1 0.5 / tick 2 1.0 —— 照常运行
怎么找出代码里哪里阻塞了循环？
开调试模式：asyncio.run(main(), debug=True) 或设置环境变量 PYTHONASYNCIODEBUG=1，执行超过 100 毫秒的回调会被记进日志（阈值可以通过 loop.slow_callback_duration 调整）。3.12 实测会打印类似 Executing <Task ...> took 0.313 seconds 的警告。
Node 里有同样的病吗？
有：fs.readFileSync、巨大的 JSON.parse、同步的加密计算一样会卡住 Node 的事件循环。病根相同：单线程事件循环里不能做长时间的同步工作。
必考

协程和线程有什么区别？

30 秒回答

线程由操作系统抢占式调度，任何两条字节码之间都可能被切走，所以共享数据要加锁；每个线程有自己的栈，开到几千个就很吃内存。协程由事件循环协作式调度，只在 await 的地方让出，切换时机写在代码里，开销极小，一个线程能跑十万级的协程。代价是协程不能利用多核，而且一个协程不让出，就卡住所有协程。

协程就不需要锁了吗？
不完全是。两个 await 之间的代码不会被打断；但如果一段逻辑是"读 → await → 写"，跨过了 await，别的协程可能在中间改了数据，这时要用 asyncio.Lock。
必考

既然有 GIL，多线程为什么还要加锁？

考察点

理解 GIL 只保护"单条字节码"，不保护"读-改-写"这种多步操作。这题的复现很有讲究，见下文。

30 秒回答

因为 GIL 只保证同一时刻只有一个线程在执行字节码，不保证"读-改-写"这种多步操作不被打断。n += 1 实际是"读 n、加 1、写回 n"几步，线程可能在读完之后、写回之前被切走，另一个线程的更新就被覆盖了。官方 FAQ 明确列出：L.append(x)、D[x] = y 这类单个操作是原子的，而 i = i + 1 不是。多线程修改共享数据，用 threading.Lock 包起来（with lock:），或者用线程安全的 queue.Queue 传递数据。

1 分钟复现（3.12 实测，4 个线程）

import threading, time
def run(target):
    global n
    n = 0
    ts = [threading.Thread(target=target) for _ in range(4)]
    for t in ts: t.start()
    for t in ts: t.join()
    return n

def naive():                         # 裸写 n += 1，每个线程 100 万次
    global n
    for _ in range(1_000_000): n += 1
def one(): return 1
def with_call():                     # 读 n 和写 n 之间夹了一次函数调用
    global n
    for _ in range(1_000_000): n += one()
def with_yield():                    # 读和写之间主动让出，每个线程 1000 次
    global n
    for _ in range(1000):
        tmp = n; time.sleep(0); n = tmp + 1

print(run(naive))        # 4000000 —— 没丢，但这不是保证（见追问）
print(run(with_call))    # 1813320 —— 预期 400 万，丢了一大半
print(run(with_yield))   # 1155    —— 预期 4000
# 后两个数每次运行都不一样，但都明显少于预期
为什么裸写的 n += 1 在 3.12 上没丢？
实测说明：在 3.12 上，解释器切换线程的检查点恰好没落在裸写 n += 1 的读和写之间，所以没丢；中间插一次函数调用，就出现了大量丢失。这是解释器的实现细节，官方 FAQ 依然把它列为非原子操作。换个写法、换个版本、换成自由线程版本都可能出错。网上很多"多线程计数器"演示在新版本上已经复现不出来了——千万别得出"我试过不会丢，所以是安全的"这种结论。

常见错误

"有 GIL 所以线程安全"。

必考

多进程之间怎么通信？多进程有什么代价？

30 秒回答

进程之间不共享内存，所以多进程能绕开 GIL 真正并行，代价也在这里：传给子进程的参数和返回值都要用 pickle 序列化、再反序列化，大对象来回传很慢；进程间要共享数据，得用 multiprocessing 的 Queue、Pipe，或者 3.8 起的 shared_memory。每个进程还要单独加载解释器和模块，启动慢、占内存，所以小任务用多进程反而不划算。启动方式有三种：spawn（启动一个全新的解释器，是 Windows 和 macOS 的默认）、fork（复制父进程）、forkserver（3.14 起成为 Linux 等 POSIX 平台的默认，以前是 fork）。spawn 和 forkserver 都会在子进程里重新导入主模块，所以主程序必须写在 if __name__ == '__main__': 下面。

为什么小任务用多进程反而慢？
实测：两次 1000 万次循环，串行 0.64 秒，两个进程 0.65 秒——进程启动和通信的开销把并行收益吃掉了；工作量加到 4000 万次后，两个进程才明显更快（1.85 秒对比 3.12 秒）。
fork 有什么问题？
fork 会复制父进程的全部状态，但只复制调用 fork 的那个线程。如果父进程里有别的线程正持有锁，子进程里这把锁就永远没人释放，可能死锁——官方文档也提醒，对多线程进程安全地 fork 很难。
必考

concurrent.futures 怎么用？线程池默认开多少个线程？

30 秒回答

concurrent.futures 给线程池和进程池提供了统一接口：ThreadPoolExecutor 和 ProcessPoolExecutor 都用 submit 提交单个任务（返回一个 Future），用 map 批量执行，用 as_completed 按完成顺序取结果，换池子只要换一个类名。默认线程数：3.13 起是 min(32, (os.process_cpu_count() or 1) + 4)，之前用的是 os.cpu_count()——很多资料还停留在旧公式上；进程池默认等于 CPU 数。

1 分钟复现（3.12 实测）

import time
from concurrent.futures import ThreadPoolExecutor
def io_task(i):
    time.sleep(1)                         # 模拟一次 1 秒的网络请求
    return i

t = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as ex:
    print(list(ex.map(io_task, range(5))))    # [0, 1, 2, 3, 4]
print(round(time.perf_counter() - t, 1))      # 1.0 —— 5 个"请求"并发，不是 5 秒
print(ThreadPoolExecutor()._max_workers)      # 24 —— 本机 20 核：min(32, 20 + 4)
必考

asyncio 里怎么控制并发数和超时？gather 和 TaskGroup 有什么区别？

30 秒回答

三件事。限制并发数用 asyncio.Semaphore：用 async with sem: 包住要限制的调用，同一时刻最多 N 个进去。超时用 asyncio.timeout（3.11 起）或 asyncio.wait_for。批量并发用 gather 最简单，但要知道：其中一个任务出错时，异常会立刻抛给调用方，别的任务不会被取消、会继续跑；3.11 起的 TaskGroup 在有任务失败时会取消组里其余的任务，更适合"要么都成功、要么一起停"的场景。

1 分钟复现（3.12 实测）

import asyncio, time
async def call_llm(i, sem, t0):
    async with sem:                               # 同一时刻最多 2 个进来
        print('start', i, round(time.perf_counter() - t0, 1))
        await asyncio.sleep(1)
async def main():
    sem = asyncio.Semaphore(2); t0 = time.perf_counter()
    await asyncio.gather(*(call_llm(i, sem, t0) for i in range(5)))
asyncio.run(main())
# start 0 0.0 / start 1 0.0 / start 2 1.0 / start 3 1.0 / start 4 2.0

async def ok(name):
    await asyncio.sleep(0.5); print(name, '完成')
async def boom():
    await asyncio.sleep(0.1); raise ValueError('boom')
async def use_gather():
    try:
        await asyncio.gather(ok('A'), boom())
    except ValueError:
        print('gather 收到异常')
    await asyncio.sleep(0.6)
async def use_taskgroup():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ok('B')); tg.create_task(boom())
    except* ValueError:
        print('TaskGroup 收到异常组')
    await asyncio.sleep(0.6)
asyncio.run(use_gather())      # gather 收到异常 / A 完成   —— A 没被取消，还在跑
asyncio.run(use_taskgroup())   # TaskGroup 收到异常组      —— B 被取消了

项目故事（迁移讲法）

「我在 Node 项目里用 p-queue 把 GLM 调用限制在同时 2 个，避免撞上团队共享 API 的限流；遇到 429 时先释放名额再退避等待，等完重新排队，避免占着名额干等。换到 Python 就是 asyncio.Semaphore(2)，退避等待写在 async with 块的外面。」

以为 gather 里一个任务出错，其他任务会自动停下——不会，它们继续在后台跑。

必考

听说 Python 已经有无 GIL 的版本了？现在是什么状态？

30 秒回答

有，叫自由线程版（free-threaded），是去掉了 GIL 的 CPython 构建（PEP 703）。3.13 首次以实验性质提供（可执行文件叫 python3.13t）；3.14 起按 PEP 779 获得官方支持，但仍然是一个单独的可选版本，不是默认版本；到 3.15 依然不是默认。它让多个线程能真正并行跑 Python 代码，代价是单线程性能有损失（3.14 的文档说大约 5–10%），依赖的 C 扩展也需要适配。另一个影响：以前被 GIL"碰巧掩盖"的线程安全问题会更容易暴露，该加的锁一个都不能少。

进阶追问

进阶

asyncio 服务里有一段 CPU 密集的计算，该怎么处理？

30 秒回答

不能直接在协程里算，会卡住事件循环（同第 4 题）。也不要指望 asyncio.to_thread：线程里跑纯 Python 计算会和事件循环争抢 GIL，循环不至于完全卡死，但会明显变慢。正确做法是交给进程池：loop.run_in_executor(进程池, 函数, 参数)。计算量特别大或耗时特别长的任务，干脆放进 Celery 这类任务队列，由单独的 worker 进程处理，Web 服务只负责派发任务和查询结果。

import asyncio
from concurrent.futures import ProcessPoolExecutor

def backtest(params):                         # CPU 密集；必须是模块级函数，才能被 pickle
    ...

pool = ProcessPoolExecutor(max_workers=2)     # 全局复用，别每个请求都新建

async def handler(params):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(pool, backtest, params)
进阶

协程是怎么实现的？调用一个 async 函数时，Python 和 JS 有什么不同？

30 秒回答

async def 定义的叫协程函数，调用它不会执行函数体，只返回一个协程对象；协程对象要么被 await，要么交给事件循环（asyncio.run、create_task）才会开始执行。协程的思想来自生成器：都能暂停、交出控制权、之后从暂停的地方恢复，事件循环就是在 I/O 就绪时把协程推回去接着执行。这里和 JS 很不一样：JS 里调用 async 函数，会立刻同步执行到第一个 await；Python 里调用协程函数，一行都不执行。

1 分钟复现（3.12 实测）

import asyncio
async def hello():
    print('执行了')

hello()                # 什么都没打印，只得到警告：
                       # RuntimeWarning: coroutine 'hello' was never awaited
asyncio.run(hello())   # 执行了
那"忘了写 await"会怎样？
协程根本没跑，而且不报错、只给一个警告。比如忘了 await 一个写库的协程，数据就悄悄没写进去。JS 里忘了 await，函数至少还会在后台执行完；Python 里是完全没执行——这是从 Node 转过来最容易犯的错误之一。
进阶

死锁是怎么产生的？怎么避免？

30 秒回答

死锁是两个或多个线程互相等待对方持有的锁，谁都走不下去。经典成因：线程 1 先拿 A 再拿 B，线程 2 先拿 B 再拿 A。避免办法：所有地方按固定顺序加锁；加锁时带超时（lock.acquire(timeout=...)），拿不到就放弃并重试；用 with 保证锁一定被释放；同一个线程需要重复获取同一把锁的场景，用 RLock（可重入锁）——普通 Lock 被同一个线程重复获取，会把自己锁死。

1 分钟复现（3.12 实测）

import threading
lock = threading.Lock()
print(lock.acquire(), lock.acquire(timeout=1))     # True False —— 同一线程第二次拿不到
                                                    #（不加 timeout 就永远卡在这里）
rlock = threading.RLock()
print(rlock.acquire(), rlock.acquire(timeout=1))   # True True —— 可重入锁允许重复获取
线上程序卡死了，怎么判断是不是死锁？
用 py-spy dump --pid 进程号 打印每个线程此刻的调用栈，不用重启进程；如果几个线程都停在 acquire 上，基本就是死锁。

场景排障题

场景

FastAPI 服务一到高并发，所有接口一起变慢甚至超时，连健康检查都慢。怎么排查？

答题框架

"所有接口一起慢"而不是"某个接口慢"，说明是共享资源被占满：要么事件循环被阻塞，要么线程池或连接池耗尽。

30 秒回答

先确认现象：连最简单的健康检查接口都变慢了，说明问题出在共享的事件循环上，而不是某个业务接口本身。第一怀疑对象：某个 async def 路由里调用了同步阻塞代码（requests、time.sleep、同步数据库驱动），它一执行，整个事件循环都停下来。排查：用 py-spy dump --pid 看事件循环所在线程此刻卡在哪一行，不用重启服务；或者在预发环境开 asyncio 调试模式，超过 100 毫秒的回调会被记录。修复三选一：换成异步库；用 asyncio.to_thread 把同步调用挪到线程里；或者干脆把这个路由改成普通 def——FastAPI 会把 def 路由放到线程池里执行，不会阻塞事件循环。

改成普通 def 就万事大吉了吗？
不是。def 路由跑在线程池里，线程池有上限；大量慢请求会把线程池占满，后面的请求开始排队——问题从"卡住事件循环"变成了"线程池耗尽"。根本解法还是让慢的 I/O 走异步库，或者把耗时任务挪到任务队列。

项目对照

「这和 Node 里在请求处理中调用 fs.readFileSync 是同一个病。我的 Node 服务在流式对话时每 15 秒发一次保活帧，事件循环一旦被卡住，保活帧也发不出去，前端 90 秒的看门狗就会断开连接——在流式服务里，事件循环被阻塞会直接表现为成片的断流。」

场景

同事用多线程给一段数据计算"加速"，结果反而更慢了。为什么？怎么改？

30 秒回答

先判断任务类型：纯 Python 的计算是 CPU 密集，在默认版本的 CPython 里受 GIL 限制，多个线程只能轮流执行，再加上线程切换和争抢 GIL 的开销，常常不比串行快，甚至更慢。实测：两次 1000 万次循环，串行 0.64 秒，两个线程 0.83 秒，反而更慢；工作量加到两次 4000 万次，串行 3.12 秒、两个线程 2.90 秒，基本没加速，而两个进程是 1.85 秒。改法：CPU 密集改用多进程（注意进程启动和数据序列化的开销，小任务不划算）；能向量化的交给 numpy 这类会释放 GIL 的 C 扩展；或者评估自由线程版本。复现代码见第 1 题。

场景

一个多进程脚本在 Linux 上好好的，拿到 Windows 上一跑就报错。为什么？

30 秒回答

Windows（以及 macOS）默认用 spawn 启动子进程：子进程会启动一个全新的解释器，并重新导入主模块。如果创建进程池的代码直接写在模块顶层，子进程导入时又会去创建进程池，于是报错——3.12 实测报 RuntimeError，提示当前进程还没完成启动阶段。修复：把启动代码放进 if __name__ == '__main__': 下面。另一个常见错误：交给进程池的函数和参数必须能被 pickle，lambda、函数内部定义的函数、数据库连接、锁都不行——实测把 lambda 交给进程池会报 PicklingError。

1 分钟复现（3.12 实测，存成文件运行）

# bad.py —— 在 Windows 上运行会报 RuntimeError：
#   An attempt has been made to start a new process before the
#   current process has finished its bootstrapping phase.
from concurrent.futures import ProcessPoolExecutor
def sq(x): return x * x
with ProcessPoolExecutor(2) as ex:            # 顶层直接创建进程池
    print(list(ex.map(sq, range(4))))

# good.py
from concurrent.futures import ProcessPoolExecutor
def sq(x): return x * x
if __name__ == '__main__':
    with ProcessPoolExecutor(2) as ex:
        print(list(ex.map(sq, range(4))))      # [0, 1, 4, 9]
        # 换成 ex.map(lambda x: x * x, range(4)) 会报：
        # PicklingError: Can't pickle <function <lambda> ...>
为什么这段代码以前在 Linux 上不写保护也能跑？
以前 Linux 默认用 fork，子进程直接复制父进程，不重新导入主模块。3.14 起 Linux 默认改成了 forkserver，它也会重新导入主模块。所以现在无论什么平台，都应该写 main 保护。
