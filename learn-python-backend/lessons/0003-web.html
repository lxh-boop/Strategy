必考八股

必考

WSGI 和 ASGI 是什么？有什么区别？

考察点

分清"规范 / 框架 / 服务器"三层，这是 Python Web 面试的第一道门槛。

30 秒回答

它们都是"Web 服务器和应用框架之间怎么对接"的接口规范，不是框架也不是服务器。WSGI（PEP 3333）是同步时代的规范：服务器每来一个请求就调用一次应用，应用返回响应，一问一答、一请求一调用，天然不支持长连接和异步。ASGI 是它的异步后继者：把通信改成异步消息（receive / send 两个异步通道），同一个连接上可以收发多次，所以能支持 WebSocket、HTTP/2 这类协议，也能跑 async 应用。生态对应：WSGI 框架有 Django、Flask，服务器有 gunicorn、uWSGI；ASGI 框架有 FastAPI、Django（3.0 起也支持 ASGI），服务器有 uvicorn、daphne、hypercorn。类比 Node：ASGI 之于 WSGI，就像 Node 的异步模型之于传统的每请求一线程模型。

1 分钟复现（3.12 实测）

看一眼 WSGI 长什么样（标准库自带服务器，无需安装任何东西）：

# wsgi_demo.py —— python wsgi_demo.py 直接运行
from wsgiref.simple_server import make_server
def app(environ, start_response):          # WSGI 应用：一个普通函数
    start_response('200 OK', [('Content-Type', 'text/plain')])
    return [b'hello wsgi, path=' + environ['PATH_INFO'].encode()]
server = make_server('127.0.0.1', 8000, app)
server.serve_forever()
# 浏览器访问 http://127.0.0.1:8000/books → hello wsgi, path=/books
Django 和 Flask 是哪个阵营？
都能跑：Django 3.0 起同时支持 WSGI 和 ASGI；Flask 是 WSGI 框架（要跑在 ASGI 服务器上得靠适配层）；FastAPI、Starlette 是原生 ASGI。

常见错误

把 WSGI 说成"Python 的 Web 框架"，或者以为 ASGI 是框架。

必考

Django、Flask、FastAPI 各适合什么场景？怎么选？

30 秒回答

Django 是"全家桶"：ORM、Admin 后台、认证、迁移、模板全带，自带一套约定，适合内容型网站、后台管理系统这类标准业务；用它的官方 LTS 版本最省心。Flask 是微框架：核心只有路由和请求上下文，其他（数据库、校验、认证）按需自己装，灵活但要自己搭，适合小服务、原型和自定义程度高的项目。FastAPI 是基于 Starlette 和 Pydantic 的现代 ASGI 框架：类型注解即文档即校验，自动生成 OpenAPI/Swagger，原生 async，性能好，适合 API 服务和微服务，也是 AI 应用接口（配合大模型 SDK）的主流选择。一句话：要全家桶选 Django，要轻和自由选 Flask，要现代异步 API 选 FastAPI。

和 NestJS 对比？
NestJS 像 Django：强约定、依赖注入、全家桶式的模块组织；FastAPI 像"Express + 类型安全 + 自动文档"的组合。我在 Node 项目里靠 class-validator + Swagger 装饰器拼出来的东西（校验 + 文档），FastAPI 靠类型注解原生就给。
必考

FastAPI 为什么快？async def 和 def 路由有什么区别？

考察点

FastAPI 的两个性能来源 + def/async def 的执行差异——官方文档有明确说法，别背"它用了异步所以快"这种含糊答案。

30 秒回答

两个来源：① 底层是 Starlette（ASGI 工具箱）+ uvicorn（异步服务器），本身 I/O 就快；② 数据校验靠 Pydantic v2，它的核心校验逻辑在独立的 pydantic-core 包里，大部分类型是用 Rust 实现的，校验很快。async def 和 def 路由的区别要背准（官方文档原话）：async def 路由直接在事件循环里运行，里面不能有阻塞调用；普通 def 路由会被放进外部线程池执行（然后被 await），阻塞了也不影响事件循环。依赖项也遵守同样的规则。

所以普通 def 更安全？
只是不会卡事件循环，但线程池有上限（默认大小由 anyio 决定，通常 40），大量慢请求会把线程池占满，后面的请求排队。根本解法还是让 I/O 走异步库。

加分项

类型注解在 FastAPI 里被"读"出来用：参数声明的类型决定校验规则和文档，这正好利用了"注解保留在运行时"的特性（见第一课第 16 题）。

必考

Pydantic 是什么？为什么它快？和手写校验比好在哪？

30 秒回答

Pydantic 是基于类型注解的数据校验和解析库：定义一个继承 BaseModel 的类，字段写上类型，传入数据就自动做类型转换和校验，不合法抛 ValidationError（带字段级的错误明细）。快的原因：v2 的核心校验逻辑在独立的 pydantic-core 包里，大部分类型用 Rust 实现。和手写校验比：声明式、和 FastAPI 深度集成（路由参数直接用它校验）、还能导出 JSON Schema。另外它顺带做类型强转——传字符串 "5" 给 int 字段会转成 5，宽松但好用。

1 分钟复现（3.12，本机 Pydantic 2.13.5 实测）

from pydantic import BaseModel, Field, ValidationError

class CreateStrategy(BaseModel):
    name: str = Field(min_length=1, max_length=50)
    rebalance_days: int = Field(gt=0, le=60)
    factors: list[str]

print(CreateStrategy(name='mom', rebalance_days='5', factors=['PE']))
# name='mom' rebalance_days=5 factors=['PE']   —— '5' 被转成了 int

try:
    CreateStrategy(name='', rebalance_days=0, factors=[])
except ValidationError as e:
    print(e.error_count(), [err['loc'][0] for err in e.errors()])
# 2 ['name', 'rebalance_days'] —— 每个字段的错误单独报出来
settings（环境变量、配置文件）怎么校验？
pydantic-settings：BaseSettings 子类里声明字段类型，自动从环境变量读取并校验——对应 Node 里的 @nestjs/config 加 zod 校验。

常见错误

说"Pydantic 是用 Rust 写的框架"——准确说法是核心校验逻辑（pydantic-core）大部分用 Rust 实现，Pydantic 本身是 Python 库。

必考

什么是 N+1 查询？怎么解决？

考察点

ORM 最经典的性能问题：概念 + 检测 + 解法，最好能说出自己用什么工具检测。

30 秒回答

查 N 条主记录，再对每条主记录单独发一条 SQL 查关联对象，总共 1 + N 条查询。典型代码：查出所有订单，循环里访问 order.user.name，每次访问都触发一条新查询。列表页 100 行就是 101 条 SQL，页面慢一半以上都可能是它。解法按场景选：预加载（Django 的 select_related 用 SQL JOIN 一次查回外键关联，prefetch_related 对多对多等关系分两条查询再在内存里拼，SQLAlchemy 的 joinedload/selectinload 同理）；或者干脆只查需要的列，不碰关联对象。检测：开发环境打印 SQL 日志数条数；Django 有现成的 assertNumQueries 断言；MySQL 侧看慢日志里同一模式的查询短时间重复出现。

1 分钟复现（3.12，本机 SQLAlchemy 2.0.53 实测，标准库 sqlite，无需装数据库）

from sqlalchemy import create_engine, event, ForeignKey, select
from sqlalchemy.orm import (DeclarativeBase, Mapped, mapped_column,
                            relationship, Session, joinedload, selectinload)

class Base(DeclarativeBase): pass
class Author(Base):
    __tablename__ = 'author'
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    books: Mapped[list['Book']] = relationship(back_populates='author')
class Book(Base):
    __tablename__ = 'book'
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    author_id: Mapped[int] = mapped_column(ForeignKey('author.id'))
    author: Mapped[Author] = relationship(back_populates='books')

engine = create_engine('sqlite://')          # 内存库，跑完即销毁
Base.metadata.create_all(engine)
with Session(engine) as s:
    s.add_all([Book(title=t, author=Author(name=t.upper())) for t in 'abc'])
    s.commit()

queries = 0
@event.listens_for(engine, 'before_cursor_execute')
def _count(*_):
    global queries; queries += 1

def run(stmt, touch):                        # 执行查询，触碰到关联属性，返回 SQL 条数
    global queries
    with Session(engine) as s:
        queries = 0
        for obj in s.scalars(stmt).unique():
            touch(obj)
    return queries

print(run(select(Book), lambda b: b.author.name))                              # 4 —— 1 查书 + 3 查作者
print(run(select(Book).options(joinedload(Book.author)),
          lambda b: b.author.name))                                            # 1 —— JOIN 一次带回
print(run(select(Author).options(selectinload(Author.books)),
          lambda a: [b.title for b in a.books]))                              # 2 —— 查作者 1 条 + 批量查书 1 条
select_related 和 prefetch_related 怎么选？
外键、一对一这种"每个主记录对应一条"的关系用 select_related（一条 JOIN）；多对多、反向一对多用 prefetch_related（两条查询，避免 JOIN 造成的行数爆炸）。
不用 ORM 怎么避免？
一条 SQL 用 JOIN 或 WHERE id IN (...) 批量取回，在应用层拼装——本质和 prefetch_related 相同。

项目对照

「我的 Node 项目用 mysql2 手写 SQL，取策略列表时是显式的一条 JOIN 或两条批量查询，所以没踩过 ORM 的 N+1；但这个坑让我在 review 任何 ORM 代码（包括以后用 Python）时会专门数查询条数。」

必考

SQLAlchemy 的连接池是怎么工作的？默认参数是什么？pool_pre_ping 解决什么问题？

考察点

连接池模型 + "MySQL 服务器等 8 小时无活动就断开连接"这个经典线上问题的解法。

30 秒回答

create_engine 默认带 QueuePool 连接池：用完的连接不销毁，放回池里给下一个请求复用，省掉每次握手认证的开销。默认参数：pool_size=5（常驻连接数）、max_overflow=10（高峰临时多开的量，用完归还后关闭）、pool_timeout=30（池满时最多等 30 秒，超时报错）、pool_recycle=-1（不主动回收）。pool_pre_ping 解决"连接被服务端单方面断开"的问题：每次从池里取出连接前先发一个轻量探活包，连接死了就 transparently 重建——MySQL 默认 8 小时无活动就断开（wait_timeout），长驻进程第二天早上第一波请求报 "MySQL server has gone away"，经典解法就是 pre_ping 或把 pool_recycle 设成小于 wait_timeout 的值。

1 分钟复现（3.12 实测）

from sqlalchemy import create_engine
engine = create_engine('sqlite://')          # sqlite 也走同一套池化接口
p = engine.pool
print(type(p).__name__, p.size(), p._max_overflow, p._timeout, p._recycle)
# QueuePool 5 10 30.0 -1
连接数怎么算才不会超？
单实例最多 pool_size + max_overflow。我的 Node 项目两个实例各配 20，就是按"MySQL 默认 max_connections=150，留足余量"算的；SQLAlchemy 默认 5+10=15 更保守，多实例部署时同样要乘以实例数去对 max_connections。
async 环境呢？
用 create_async_engine + 异步驱动（asyncpg/aiomysql），池机制相同；FastAPI 的依赖项里获取会话、请求结束自动归还。

项目故事（迁移讲法）

「我在 Node 项目里用 mysql2 的连接池（上限 20）+ 每次查询显式拿连接，还专门做过"两实例 × 20 连接 ≤ max_connections"的容量核算。SQLAlchemy 的 QueuePool 是同一套思路，参数名不同而已。」

必考

Django ORM 的 select_related 和 prefetch_related 有什么区别？

30 秒回答

都是解决 N+1 的预加载手段，机制不同：select_related 用 SQL JOIN 把外键、一对一关联的对象在同一条查询里带回来，适合"多对一"方向；prefetch_related 对每种关联各发一条独立查询（第二次用 WHERE id IN (...) 批量取），在 Python 层把结果拼起来，支持多对多和反向关系，JOIN 会让结果集行数相乘的场景也用它。同一条 QuerySet 上可以链式组合两者。

Book.objects.select_related('author')                 # 1 条 JOIN
Author.objects.prefetch_related('books')              # 2 条：作者 + 批量取书
Book.objects.select_related('author').only('title', 'author__name')   # 顺带只取需要的列
不写参数的 select_related 会怎样？
Django 6.1 起已弃用、将在下个大版本移除——要显式写关联字段名。顺带这也是个"版本时效"考点：旧资料里的无参写法已经过时。
必考

Django 的中间件机制是怎样的？和 NestJS 的拦截器像吗？

30 秒回答

中间件是插在请求和响应之间的钩子层。请求进来按 MIDDLEWARE 列表从上往下依次经过每个中间件，响应回去时按相反顺序走——官方文档就叫它"洋葱模型"。常见用途：安全头、session、认证、CSRF、日志。和 NestJS 对比：NestJS 的中间件/守卫/拦截器/管道是一组分工更细的钩子（守卫管鉴权、管道管校验、拦截器管响应变换），Django 中间件是一个类里统一处理进和出——概念同源，粒度不同。

class TimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response      # 下一个环节（洋葱的里层）
    def __call__(self, request):
        start = time.perf_counter()           # 进入：请求阶段（从外往里）
        response = self.get_response(request)
        print(time.perf_counter() - start)    # 返回：响应阶段（从里往外）
        return response
必考

Django 怎么管理数据库事务？atomic 是怎么工作的？

30 秒回答

两种粒度。全局：ATOMIC_REQUESTS=True 让每个请求默认包在一个事务里，视图成功整体提交，抛异常整体回滚——省心但长事务多，按需关闭。局部：用 transaction.atomic() 上下文管理器或装饰器，块内成功提交、抛异常回滚；嵌套的 atomic 用 savepoint 实现，内层失败可以只回滚到保存点，外层还能继续。注意事务里别放外部调用（发邮件、调第三方接口）：回滚只回滚数据库，外部世界的副作用收不回来。

项目对照

「我的 Node 项目在保存策略时先删后插、还带 seq 递增落库，这类多步写就该包在一个事务里——我当时是靠"先写库再提交"的顺序约定保证的，换成 Django 的 atomic 或 SQLAlchemy 的 session 事务会更硬。」

必考

gunicorn 和 uvicorn 是什么关系？worker 数怎么定？

30 秒回答

gunicorn 是 WSGI 服务器（也可通过 worker 类支持 ASGI），uvicorn 是 ASGI 服务器。gunicorn 的角色是"进程管理器"：按配置预 fork 出多个 worker 进程来吃满多核、崩溃自动重启；uvicorn 单进程跑事件循环。组合拳：gunicorn -k uvicorn.workers.UvicornWorker app:app——gunicorn 管进程，每个 worker 里跑一个 uvicorn 事件循环。worker 数的官方建议公式是 (2 × CPU 核数) + 1，sync worker 的起点值；异步 worker 单进程就能扛很多并发，核数就是另一个维度了。注意 uvicorn 官方文档已把 uvicorn.workers 标记为弃用，推荐改用独立的 uvicorn-worker 包——这是一个"答出来说明你看过新文档"的点。uvicorn 自己也支持 --workers（spawn 方式，Windows 可用），简单部署可以不引 gunicorn。

gunicorn 默认 30 秒超时是怎么回事？
sync worker 超过 timeout（默认 30 秒）没有心跳，master 会认定它卡死并杀掉重启。长任务（大文件处理、长计算）在 sync worker 里会被误杀——要么换 gthread/gevent worker，要么把长任务挪到 Celery，要么调大 timeout。

项目故事（迁移讲法）

「这个结构和 PM2-cluster 很像：master 管多个 worker、崩了拉起。我 Node 项目的部署规划里，多实例 + 网关的方案对 Python 服务同样适用——gunicorn 的多 worker 就是"单机多实例"。」

必考

Celery 是什么？架构是怎样的？为什么要有任务队列？

30 秒回答

Celery 是 Python 的分布式任务队列：把耗时或需要异步执行的工作（发邮件、视频转码、大报表）从 Web 请求里拆出来。三个角色：生产者（Web 应用调用 task.delay()）、broker（消息中间件，常用 Redis 或 RabbitMQ，负责传递任务消息）、worker（独立进程，从 broker 取任务执行），结果可以写回 result backend。价值：请求立刻返回（用户体验），重活由专门的 worker 慢慢干，worker 可以独立扩容和重启，任务失败可重试。

怎么保证任务不丢？
task_acks_late=True：任务执行完才确认（默认是一拿到就确认，worker 半路挂了任务就丢）。代价是 worker 崩溃时任务会被重新投递、可能执行多次——所以晚确认的任务必须设计成幂等的。这和消息队列的 at-least-once 语义是同一件事。
你项目里的对应物？
我的 Node 项目有进程内作业（摘要折叠 job），多实例化方案里它们要剥离成独立 worker 并加分布式锁——Celery 就是 Python 生态里这件事的标准答案。
必考

Python 的日志体系是怎么设计的？多进程写同一个日志文件有什么问题？

30 秒回答

logging 模块是分层设计：Logger（记录器，按名字分层，如 app.api）产生 LogRecord，经 Handler（决定输出到哪：控制台、文件、网络）用 Formatter 格式化输出，Level 过滤级别，还可以加 Filter。分层的好处是给 app.api 配置会继承到子 logger，库作者用 getLogger(__name__) 不抢应用的配置。多进程写同一个日志文件是官方文档明确不支持的：多个进程各持文件指针，会互相覆盖、交错。解法：每个进程写自己的文件再聚合；用 QueueHandler 把日志通过队列发给单独的进程写盘；或者最简单——只写 stdout，交给容器/采集器收走（和容器日志最佳实践一致，我在 Node 项目里就是这么做的：logger 同步写 console 和按日文件）。

RotatingFileHandler 多进程能用吗？
不能安全地用：轮转时多进程会互相竞争重命名，导致丢日志或写错文件。标准轮转方案是 logrotate 这类外部工具（配合 copytruncate），或集中式日志。

Python 怎么做依赖注入？和 NestJS 的 DI 比呢？

30 秒回答

Web 层的标准答案是 FastAPI 的依赖注入系统：依赖就是一个普通函数（或类），用 Depends(依赖) 声明，框架在每次请求时调用它、把结果注入进来，支持嵌套依赖、yield 型依赖（请求结束自动清理，相当于 setup/teardown）、按需覆盖（测试时 app.dependency_overrides 换成假实现）。和 NestJS 的差别：NestJS 是全局 IoC 容器，服务按 token 注册成单例，构造时自动注入；FastAPI 的依赖是"每次请求时求值"的函数，天然请求级作用域，没有全局容器。Python 生态也有 injector、punq 这类容器库，但社区主流更偏向显式传参 + FastAPI Depends。

from fastapi import Depends, FastAPI
app = FastAPI()

def get_session():
    with Session(engine) as session:      # yield 前 = 进入，之后 = 请求结束清理
        yield session

@app.get('/books')
def list_books(session: Session = Depends(get_session)):
    return session.scalars(select(Book)).all()

加分项

依赖覆盖让测试很干净：不用启动真实数据库，覆盖成内存版即可——和 NestJS 测试里 overrideProvider 同一个思想。

进阶

Gunicorn 的 sync worker 和 gthread/gevent worker 有什么区别？长任务被杀是怎么回事？

30 秒回答

sync worker：一个进程同一时刻只处理一个请求，处理完才接下一个，并发能力 = worker 数，简单可靠，适合短请求。gthread：每个 worker 进程里再开一个线程池，一个进程能并发多个请求，适合 I/O 多的普通应用。gevent：用协程（greenlet + monkey-patch 把阻塞库改成协作式），单进程高并发，但要求整条调用链兼容。长任务被杀的机制：gunicorn 有心跳机制，sync worker 超过 timeout（默认 30 秒）没通知 master，就被认定卡死、杀掉重启——所以大文件、长计算在 sync worker 下会被误杀。解法：长任务进 Celery；或换 gthread/gevent 并调大 timeout。

怎么快速判断该用哪种 worker？
请求短、要稳 → sync 多开几个；请求以 I/O 等待为主 → gthread；追求单进程高并发且能用异步生态 → gevent 或干脆上 ASGI（uvicorn + FastAPI）。
进阶

Celery 的任务"丢过"或"重复执行过"，分别是什么原因？

30 秒回答

丢任务：默认 acks_late=False，worker 一拿到任务就确认，之后 worker 崩溃，这条任务就永远丢了。重复执行：开了 acks_late 后，worker 执行到一半崩溃，任务没确认，broker 会把它重新投递给别的 worker——执行了两次。Redis 做 broker 还有一个隐蔽坑：visibility_timeout 默认 1 小时，任务执行超过 1 小时仍未确认，broker 就认为它丢了、重新投递，于是这条长任务被反复执行。解法：重要任务 acks_late + 幂等设计（业务唯一键去重）；长任务调大 visibility_timeout 或拆小；对执行次数敏感的任务，把状态记录在数据库里由任务自己判断是否已执行。

重试怎么配？
autoretry_for=(Exception,), retry_backoff=True：对指定异常自动重试，按指数退避（默认带随机抖动、上限 600 秒）。和我在 Node 项目里给 GLM 调用写的"429 退避重试 10 次"是同一个模式。
进阶

FastAPI 里怎么实现流式响应（SSE）？要绕过哪些代理的坑？

30 秒回答

用 StreamingResponse，content 传一个生成器（async 生成器每 yield 一段就发一段）；SSE 场景把 Content-Type 设成 text/event-stream，数据按 data: ...\n\n 的格式推。代理的坑和我 Node 项目里遇到的完全一样：nginx 默认开 proxy_buffering，会把流攒起来憋着不吐，前端收不到实时数据——解法是在响应里带 X-Accel-Buffering: no（nginx 认这个头，逐响应关缓冲），再加 proxy_read_timeout 放宽，长间隔时发心跳帧。我在 NestJS 的 SSE 实现里就是这么干的（每 15 秒一个 keepalive 帧，防前端 90 秒看门狗断开），Python 侧照搬即可。

import asyncio, json
from fastapi.responses import StreamingResponse

async def event_gen():
    yield 'data: start\n\n'
    for i in range(10):
        await asyncio.sleep(1)                       # 模拟逐步产出
        yield f'data: {json.dumps({"step": i})}\n\n'
    yield 'data: done\n\n'

@app.get('/stream')
def stream():
    return StreamingResponse(event_gen(), media_type='text/event-stream',
                             headers={'X-Accel-Buffering': 'no'})

场景排障题

场景

一个接口偶尔报 "MySQL server has gone away"，第二天早上第一波请求必现。为什么？怎么修？

答题框架

这个报错本身就指向"连接被服务端单方面断开"：长驻进程 + 连接池 + MySQL 的空闲超时，三者凑齐就是必现剧本。

30 秒回答

原因链：服务是长驻进程，连接池里的连接夜里空闲；MySQL 服务端的 wait_timeout（默认 8 小时）一到，服务端单方面断开；早上第一波请求从池里拿到的是已死连接，直接报 gone away。修复按推荐顺序：开 pool_pre_ping（取连接前先探活，官方文档说连接失效时会透明重建）；或把 pool_recycle 设成小于 wait_timeout 的值（比如 3600 秒），让连接在服务端踢之前先被换掉。验证：把 MySQL 的 wait_timeout 临时调小（如 60 秒），复现问题，加上 pre_ping 后再验证消失。预防：连接池参数进 code review 清单；监控里对这类错误码加告警。

Django 项目里对应什么？
CONN_MAX_AGE：默认 0（每请求新建连接，没有这个问题）；设成非零后才有"复用旧连接被踢"的问题。原生长连接池（OPTIONS 里的 pool）目前只支持 PostgreSQL（psycopg），MySQL 没有原生选项——这是个很多人不知道的细节。

项目对照

「我的 Node 服务 24 小时挂着，mysql2 连接池同样面对 wait_timeout——这个问题是语言无关的，解法（探活、定期回收）也一致。」

场景

gunicorn 部署的服务，某个报表接口一跑，整个服务就没响应几十秒，然后这个接口还报错了。为什么？

答题框架

两个现象分开解释：没响应 = sync worker 独占；接口报错 = worker 被 timeout 杀掉。这是同一根因的两面。

30 秒回答

原因：gunicorn 默认 sync worker，一个进程同一时刻只处理一个请求；报表接口要跑 40 秒，这 40 秒里这个 worker 完全不可用，worker 开得少时整个服务就没响应了；跑满 30 秒（默认 timeout）还没完成，master 的心跳检查判定 worker 卡死，把它杀掉重启——于是接口也报错。修复组合：报表这种长任务挪到 Celery，接口立刻返回任务号，前端轮询状态（标准解法）；短期缓解换 gthread worker 并调大 timeout；再往后这类重计算任务按并发课的思路丢进程池。预防：接入 gunicorn 的超时告警；把"单请求时长上限"作为接口设计约束（Web 请求里不该有分钟级任务）。

怎么确认是 worker 被 timeout 杀了？
gunicorn 的 error log 会出现 WORKER TIMEOUT 字样，同时看到 worker pid 被替换——这是官方定义的行为（超时未心跳即杀重启）。
场景

接手一个 Django 老项目，列表页要 8 秒才出来。说说你的排查思路。

答题框架

性能排查分层：先量（哪一段慢），再看 SQL（N+1 / 缺索引 / 取了不用的大字段），再看代码（循环里的计算、序列化），最后看架构（缓存、分页）。

30 秒回答

第一步分段计时：用中间件或 APM 看 SQL 总耗时和视图计算耗时各占多少（Django debug 工具栏能直接数查询条数）。SQL 侧三连查：日志数条数——出现 1+N 的模式就是 N+1，用 select_related / prefetch_related 治；EXPLAIN 看慢查询有没有走索引，列表页的过滤和排序字段建索引；检查是不是 SELECT * 取了大字段（用 values / only 只取需要的列）。代码侧：循环里调库、每个元素单独查库、模板里触发懒加载。架构侧：列表页该有分页（没有分页本身就是 8 秒的主因）、热点列表上缓存（Redis，注意过期策略）。收尾用断言固化：给这个接口写 assertNumQueries 测试，防止以后回归。

如果 SQL 已经很少还是慢？
慢在 Python 计算或序列化（上千个对象逐个转 dict）——用 py-spy 看热点函数，把逐对象循环改成批量操作或让数据库多做（聚合下推到 SQL）。

项目对照

「我在 Node 项目里把"取数 SQL 收口到唯一入口 + 数查询条数打日志"作为防 N+1 的手段，还有 LRU + inflight 去重挡重复查询——排查思路完全一致：先量化，再分层定位。」
