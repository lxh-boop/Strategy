Lesson 0001 · 多实例部署

多实例的 Docker 部署与管理：完整工作谱

约 40 分钟（含动手则 1.5 小时） · 本课是参考谱：所有配置都按你的真实项目写好，装好 Docker 后（Redis 轨 0002）逐段跑通即可 · 配套 管理命令速查表 · 共享术语表
你部署过单实例全栈？走这条读法 你已知道镜像/容器/run/端口/卷——§2 速览即可（分层缓存值得 30 秒，它约束 Dockerfile 写法）；§3 只看红色提示框（两个贴你项目的真实决定：duckdb → bookworm-slim、logs/memories 挂卷）；§4 只看 host.docker.internal 那行注释（容器网络栈独立，是后面一切的前提）；§5 是速查表，用到再翻。§6 开始才是你的新疆界：同镜像多容器、网关分流 + sticky、滚动发布下的状态问题——逐行读。§10 的 quiz 建议全做，检索练习对已会内容同样有效。
归档说明本页已并入对应的面试课，作为实操参考谱保留：面试讲项目前把它跑通，项目故事才经得起追问。交互式自评见主课页面。

1 · 蓝图：从单实例到目标拓扑

今天整套系统是一个进程，浏览器直连它：

浏览器 ×20 ──HTTP──> node 进程（factor-agent-server :3000）──> MySQL
                         └── 进程内存：LRU 缓存 · p-queue 闸 · 检查点
                         └── 本地文件：logs/ · memories/

你们《并发治理方案》第八节的 100 人目标形态：

浏览器 ×100
   │
   ▼
nginx（唯一入口 :80）                ← 网关，履行负载均衡职能
   │  分流 + 会话粘住（sticky）
   ├──────────────┬──────────┐
   ▼                         ▼
server 实例 A              server 实例 B      ← 同一镜像跑出的两个容器
   └────────┬─────────────────────┘
            ▼
   MySQL（共享，仍在公司机房）
   Redis（共享状态，本轨配合 Redis 轨接入）

记住三件套的层次：负载均衡是网关承担的一项职能，nginx 是承载它的软件，Docker / Compose 是把这一切装盒拉起的运行方式。本课自底向上：先把一个实例装进容器（§3–4），学会管理它（§5），再复制出第二个（§6），然后把它们编成一套（§7–8）。

2 · Docker 最小概念集

概念是什么类比 npm 世界
镜像（image）只读模板：代码 + 运行环境打包件发布到 registry 的 tarball
容器（container）镜像的一次运行实例（进程 + 隔离的文件/网络）node_modules 里跑起来的那次执行
仓库（registry）存镜像的地方（Docker Hub / 公司私有）npmjs.com
分层（layer）镜像由多层叠成，每条指令一层，未变层的缓存直接复用无——这是 Docker 特有的构建缓存
分层缓存是写 Dockerfile 的核心约束 每条指令一层；某层变了，它和它之后的所有层重跑。所以依赖清单（package-lock.json）先 COPY、装依赖，源码最后 COPY——改业务代码时几千个依赖不重装，几秒出镜像。§3 的 Dockerfile 每个顺序都是为此服务。

3 · 给 factor-agent-server 写 Dockerfile

在 factor-agent-server/ 根目录新建 Dockerfile（两段式：构建段出编译产物，运行段只带生产依赖——镜像更小、攻击面更小）：

# ---------- 构建段 ----------
FROM node:22-bookworm-slim AS build
WORKDIR /app
# 先只拷依赖清单 → 这层不常变，npm ci 结果被长期缓存
COPY package-lock.json package.json ./
RUN npm ci
# 再拷源码 → 改业务代码只重建这里以下的层
COPY tsconfig.json tsconfig.build.json nest-cli.json ./
COPY src ./src
RUN npm run build          # nest build → dist/

# ---------- 运行段 ----------
FROM node:22-bookworm-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package-lock.json package.json ./
RUN npm ci --omit=dev      # 只装生产依赖（jest/ts 等全不要）
COPY --from=build /app/dist ./dist
# logs/ 与 memories/ 不打进镜像：运行时挂卷（§4）
EXPOSE 3000
CMD ["node", "dist/main.js"]
两个贴着你项目的真实决定 ① 基础镜像用 bookworm-slim（Debian/glibc）而不是更小的 alpine（musl）：你的依赖里有 @duckdb/node-api 原生模块，musl 下的预编译二进制经常装不上或跑不起来——这是真实项目才踩得到的坑。② logs/（FileConsoleLogger 落盘）和 memories/（ADR-0007 记忆文件）是运行时状态，进卷不进镜像——否则一重建容器，日志和记忆全没。

另建一个 .dockerignore（同目录），防止把宿主机的脏东西拷进构建段：

node_modules
dist
logs
memories
.env          # 密钥绝不进镜像！配置靠 §4 的 -e / env_file 注入
test

4 · 构建并跑起第一个实例

动手（前置：Docker 已装） 终端进入 factor-agent-server/ 目录。每条命令的预期结果都标了——对不上就把输出带给 agent。
  1. 构建镜像： 
    docker build -t factor-server:0.1 .
    首次几分钟（拉基础镜像 + 装依赖）；立刻改一行 src 再 build 一次——观察依赖层直接 CACHED 跳过，这就是 §2 的分层缓存。
  2. 跑起实例 A： 
    docker run -d --name server-a -p 3001:3000 \
  -e MYSQL_HOST=host.docker.internal \
  -e USER_DB_HOST=host.docker.internal \
  -e ZHIPU_API_KEY=填你的 \
  -v factor-logs:/app/logs \
  -v factor-memories:/app/memories \
  factor-server:0.1
    返回一串容器 ID。-d 后台跑；-p 3001:3000 = 宿主机 3001 → 容器 3000；-v 把两个运行时目录挂成卷（宿主机管理的持久存储）。
  3. 验证活着： 
    docker ps                 # 列表里应有 server-a，状态 Up
docker logs -f server-a   # 应看到 Nest 启动日志；Ctrl-C 退出跟随
curl http://localhost:3001/api/docs -I   # Swagger 页应答 200
    注意 MySQL 的 host 写了 host.docker.internal——容器里的 127.0.0.1 是容器自己，不是你的 Windows；这是 Docker 网络的第一课。

5 · 管理一个容器：日常命令面

「部署」之外你点名要「管理」。单个容器的日常管理就这六组命令（完整版见速查表）：

想做什么命令要点
看谁在跑docker ps / ps -a-a 连退出的也列；STATUS 列 Up/Exited 一眼定生死
看日志docker logs -f --tail 100 server-a-f 跟随；stdout/stderr 都收——所以应用要往 stdout 打日志
看资源占用docker stats每个容器的 CPU/内存实时表；Node 服务内存缓慢爬升 = 排查起点
进容器排查docker exec -it server-a sh进去后就是容器内的 shell；exit 出来，容器不受影响
停止/删除docker stop server-a && docker rm server-a删容器不清卷——factor-memories 卷里的记忆还在
开机自启 + 崩溃自愈run 时加 --restart unless-stopped进程崩了/宿主机重启了自动拉起，除非你手动 stop 过——长驻服务基本盘

6 · 第二个实例：多实例的物理诞生

多实例的秘密朴素得惊人——同一条 docker run 再执行一次，换个名字、换个宿主端口：

docker run -d --name server-b -p 3002:3000 \
  -e MYSQL_HOST=host.docker.internal -e USER_DB_HOST=host.docker.internal \
  -e ZHIPU_API_KEY=填你的 \
  -v factor-logs-b:/app/logs -v factor-memories-b:/app/memories \
  factor-server:0.1

docker ps        # server-a 和 server-b 并排 Up——这就是「两个实例」
curl http://localhost:3002/api/docs -I
此刻你已经把第一课（Redis 轨）的假设变成了实物 容器 A 和容器 B 是两个独立进程、两套独立内存：A 里的 LRU Map 完全看不见 B 的。同一查询打两遍库、互不知晓——「进程内缓存的三个天然边界」现在跑在你的机器上，不再是示意图。它们能同时跑，靠的是宿主端口不同（3001/3002）、容器端口相同（都是 3000）——镜像不需要任何改动。

卷名也分开了（-b 后缀）——两个实例的 memories/ 各写各的，正是坏点清单里「记忆文件分叉」的实物版。多实例时代码侧要改什么，见 §9。

7 · 编排：docker compose 把它们编成一套

逐条 docker run 写命令行撑不过三个容器。compose 用一份 YAML 蓝图描述全部角色，一条命令拉起整套。新建目录 D:\cht\work\deploy-lab\，放三个文件：

compose.yaml

services:
  server-a:
    build: ../factor-agent-server          # 直接用 §3 的 Dockerfile 构建
    image: factor-server:0.1
    env_file: ../factor-agent-server/.env  # 密钥从宿主机 .env 注入，不进镜像
    environment:                           # environment 覆盖 env_file 同名变量
      MYSQL_HOST: host.docker.internal     # .env 里若写 127.0.0.1，在容器里是错的
      USER_DB_HOST: host.docker.internal
    volumes:
      - server-a-logs:/app/logs
      - server-a-memories:/app/memories
    restart: unless-stopped
    mem_limit: 1g                          # 资源上限：防单实例拖垮宿主机
    healthcheck:                           # 健康检查：见下注
      test: ["CMD", "node", "-e",
             "fetch('http://127.0.0.1:3000/api/docs').then(r=>process.exit(0)).catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s                    # Nest 启动期不算失败

  server-b:
    image: factor-server:0.1               # 不再写 build：直接复用同一镜像
    env_file: ../factor-agent-server/.env
    environment:
      MYSQL_HOST: host.docker.internal
      USER_DB_HOST: host.docker.internal
    volumes:
      - server-b-logs:/app/logs
      - server-b-memories:/app/memories
    restart: unless-stopped
    mem_limit: 1g

  redis:                                   # 为 Redis 轨 0003 预留的座位
    image: redis:7-alpine
    command: redis-server --appendonly yes --maxmemory 256mb --maxmemory-policy allkeys-lru
    volumes:
      - redis-data:/data
    restart: unless-stopped

  nginx:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"                          # 用户唯一入口
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - server-a
      - server-b
    restart: unless-stopped

volumes:
  server-a-logs: {}
  server-a-memories: {}
  server-b-logs: {}
  server-b-memories: {}
  redis-data: {}
健康检查的语义 healthcheck 让 Docker 定期戳一下 /api/docs，连续失败标记为 unhealthy——它是状态标记和重启依据（配合编排工具），不是「挂了立刻重启」的开关；「崩了拉起」由 restart 负责。两者是互补的两层保障。

compose 日常管理命令

docker compose up -d          # 按蓝图拉起整套（缺的建，变了的重配）
docker compose ps             # 全家桶状态一目了然
docker compose logs -f server-a   # 只跟某个服务的日志
docker compose restart server-a   # 只动一个角色
docker compose down           # 全套停下删容器（卷保留！数据安全）
docker compose down -v        # 连卷一起删——核选项，记忆/Redis 数据没了

进阶一步：compose 还支持 docker compose up -d --scale server-a=3 一条命令横向加实例——但需要 nginx 改用 Docker 内置 DNS 动态发现（resolver 127.0.0.11），本课先不展开，问 agent 可拿到完整改法。

8 · 网关：nginx 配置逐行讲

deploy-lab 目录里第三个文件 nginx.conf——所有用户的流量从 8080 进来，被分给两个实例：

upstream factor_server {
    # —— 会话粘住（sticky）——
    # ip_hash：同一来源 IP 固定转发到同一实例。本地实验够用；
    # 生产建议改 hash $cookie_你的会话cookie名;，按登录会话粘（NAT 下同一出口 IP
    # 的所有用户会挤到同一实例，ip_hash 在办公室网络里有这个坑）
    ip_hash;

    # 服务名直接写 compose 服务名——Docker 内置 DNS 把 server-a/server-b
    # 解析成容器内部 IP。这就是 §7 网络编排的红利：不写死 IP
    server server-a:3000;
    server server-b:3000;
}

server {
    listen 80;

    location / {
        proxy_pass http://factor_server;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # —— 流式响应三件套（你们的对话进度事件是流式推送）——
        # 不关缓冲，nginx 会把事件攒在自己内存里，憋到超时才一次性吐出
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;   # 长回答 + GLM 限流退避（~63s 窗口）不读超时
    }
}

启动并验证 sticky：docker compose up -d 后浏览器访问 http://localhost:8080/api/docs，然后分别看两个实例的日志——正常会话请求应稳定出现在同一个实例的 docker logs server-a 里（换网络/清 cookie 才可能跳到 B）。

分流是自动的，策略是你要选的 写好 upstream + proxy_pass，nginx 默认就自动轮询分流——这部分确实不用管。但默认轮询会把同一用户的请求拆到两个实例（§9 的状态问题全来了），所以 ip_hash; 是本配置里最不能删的一行。策略谱系：轮询（默认）/ least_conn（最少连接优先——你们的 GLM 调用长且耗时不均，它比轮询分得匀）/ ip_hash（按来源 IP 粘）/ hash $cookie_会话名;（按登录会话粘，生产首选）。另一个分工要知道：开源版 nginx 的故障摘除是被动式的（转发失败 max_fails 次才暂时拉黑，默认探不出"活着但很慢"）；主动定时探测是商业版功能——所以运维上是两层各管一半：compose 的 restart + healthcheck 负责把死容器拉起来，nginx 被动摘除负责别把请求发给刚死的那个。

9 · 多实例时代码侧要注意什么

拓扑搭好后，你代码里的进程内状态就是坏点清单（Redis 轨 0003 会逐个修）。先有一张对照表，动手时知道自己在修哪个：

代码里的进程内状态双容器下的症状修法（哪一轨负责）
LRU 缓存（MysqlFactorDataService）各缓存各的，命中率掉、重复打库共享 Redis 缓存（Redis 轨）
MemorySaver 检查点 / pendingResumes / pendingConfirms这一问在 A 登记挂起，下一问被分到 B → 挂起恢复失效本课的 sticky 先兜住；彻底解 = 外置 Redis（Redis 轨 + BullMQ 阶段）
p-queue 资源闸（glm=2 / backtest=2）变成 2+2=4，全局限流失效接受每实例限额，或分布式限流（远期）
memories/ 记忆文件两个卷各写各的，记忆分叉共享卷或迁入 Redis/DB（Redis 轨）
MySQL 连接池 20 ×2 实例40 连接逼近 max_connections=150 的一半注意余量，多实例前和 DBA 对一遍（部署轨意识点）
单实例从不遇到的问题：发布窗口 多实例下更新版本是滚动进行的：A 还跑 v1、B 已上 v2 的窗口里，两版代码同时连着同一个库。所以 DB 迁移必须向后兼容（先加列 → 双版共存 → 再删旧列，拆成多次发布）——一条 ALTER 连删带改的迁移会在窗口期打崩旧版。这是"每个服务只跑过一个实例"从未遇到过的坑，0003 课（滚动更新与零停机发布）的主角。

10 · 检索练习

Q1 · 改了 src 里一行代码重新 docker build，哪些层会重新执行？

回忆 §2 的分层缓存规则：某层变了，什么范围的层要重跑？为什么 Dockerfile 要把依赖 COPY 放在源码 COPY 前面？
对。缓存逐层复用，直到第一个变化层——所以 package-lock 没变时 npm ci 层直接 CACHED，改业务代码秒级出镜像。依赖在前、源码在后的顺序就是为这个服务的。

Q2 · docker run -p 3001:3000 里两个数字的含义是——

回忆 §6：server-a 用 3001:3000，server-b 用 3002:3000——两个实例容器端口一样，宿主端口不一样。谁冒号前谁冒号后？
对。浏览器访问宿主机的 3001/3002，各自转发到两个容器里相同监听的 3000——「同镜像多实例，宿主端口不同、容器端口相同」，端口映射是多实例并存的第一根杠杆。

Q3 · 容器里连 MySQL 用 host.docker.internal 而不是 127.0.0.1，因为——

回忆 §4 验证那步的注释：容器里的 127.0.0.1 是谁？每个容器有自己的什么？
对。每个容器有独立的网络栈，127.0.0.1 指容器自己——MySQL 跑在你的 Windows 宿主机上，得用 Docker 提供的 host.docker.internal 指回宿主。这是容器化改动 .env 的第一个必踩点。

Q4 · compose 里同一变量在 env_file 和 environment 都写了，谁生效？

回忆 §7 compose.yaml 里的注释：environment 的角色是「覆盖」——MYSQL_HOST 为什么要在 environment 里再写一遍？
对。environment 优先级高于 env_file——组合用法就是「.env 放共同密钥，environment 放每个服务需要覆盖的值」（如把 127.0.0.1 覆盖成 host.docker.internal）。

Q5 · nginx upstream 不配 ip_hash，用户 A 相邻两次请求可能——

回忆 §9 第二行：默认的分流策略是什么？A 的挂起状态登记在实例 1 的内存里，第二次请求到了实例 2 会发生什么？
对。默认轮询分流，相邻请求落不同实例——A 的 pendingResumes 在实例 1，下一问到实例 2 就找不到挂起现场，挂起恢复失效。sticky 不是性能优化，是进程内状态的保命符。

Q6 · restart: unless-stopped 的行为是——

回忆 §5 表格最后一行：这个策略管的是哪两件事（进程崩溃、宿主机重启）之外唯一的例外？
对。容器进程崩溃或宿主机重启都会自动恢复，唯一例外是你手动 docker stop 过——「除非手动停」。它和 healthcheck（标记状态）是互补的两层保障。
