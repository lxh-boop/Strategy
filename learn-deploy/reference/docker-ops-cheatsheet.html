单容器生命周期

命令作用要点
docker build -t 名:tag .按 Dockerfile 构建镜像缓存失效从第一个变化层开始；彻底重建加 --no-cache
docker run -d --name x -p 宿:容 镜像创建并启动容器-d 后台；-e K=V 注入环境变量；-v 卷:/路径 挂持久卷
docker ps / -a列出运行中 / 全部容器STATUS 列 Up / Exited (码) 一眼定生死
docker stop / start / restart x停止 / 启动 / 重启stop 是优雅停机（先 SIGTERM，超时才 SIGKILL）
docker rm x删除容器容器可随删，卷不受影响；运行中的要先 stop（或加 -f）
docker logs -f --tail 100 x看 / 跟日志收 stdout/stderr——应用要往 stdout 打日志
docker statsCPU / 内存实时表内存只升不降 = 排查泄漏的起点
docker exec -it x sh进容器 shell排查文件、连通性（容器内 ping/curl 另一容器名）
docker inspect x全量元数据 JSONIP、挂载、env、健康状态都在这里
docker diff x列出容器可写层里的改动A 新增 / C 修改 / D 删除；排查"谁往容器里写了东西"，确认哪些数据会随容器删除而丢
docker images / rmi镜像列表 / 删除悬空镜像（<none>）批量清：docker image prune
docker system prune清理闲置资源加 -a --volumes 更彻底——先想清楚再敲

重启策略（restart）

策略崩溃后宿主机重启后手动 stop 后
no（默认）不重启不启动—
on-failure非零退出才重启不启动保持停
unless-stopped重启启动保持停（唯一例外）
always重启启动宿主重启后仍会拉起

长驻服务基本盘：unless-stopped；配合 healthcheck（状态标记）形成两层保障。

Compose 全家桶

命令作用要点
docker compose up -d按蓝图拉起整套镜像缺了自动 build（写了 build: 的服务）；配置变了自动重配
docker compose ps全家状态含 health 状态
docker compose logs -f [服务]聚合日志不指定服务 = 全部混流，带服务名前缀
docker compose restart server-a只动一个角色其他角色不受影响
up -d --no-deps --wait server-a滚动更新单台（0003）--no-deps 不牵连其他服务；--wait 阻塞到健康检查通过才返回
RELEASE=v2 docker compose …按版本标签发布/回滚（0003）配合 image: factor-server:${RELEASE:-0.1}；当前版本钉进 compose 目录的 .env，防裸 up 回落默认值
docker compose exec server-a sh进某服务容器同 docker exec
docker compose down停并删容器与网络卷保留；-v 连卷删（核选）
up -d --scale 服务=N横向扩到 N 实例需 nginx 改用 Docker DNS 动态发现（resolver 127.0.0.11）+ 容器端口不固定映射

compose.yaml 字段速查（Lesson 0001 用到的）

字段含义踩坑点
build: / image:构建上下文 / 复用镜像名多实例只给一个服务写 build，其余 image 复用
env_file: + environment:批量注 env + 单项覆盖environment 优先级高——用它覆盖 127.0.0.1 → host.docker.internal
volumes:（命名卷）持久化运行时数据down 不删卷，down -v 才删
restart: unless-stopped崩溃/开机自愈手动 stop 是唯一例外
mem_limit: / cpus:资源上限防单容器拖垮宿主机；配合 docker stats 调参
healthcheck:健康状态探测start_period 给启动期；失败只标记状态，重启靠 restart 策略
depends_on:启动顺序只保证「先启动」，不保证「已就绪」——就绪要看 healthcheck

nginx 网关要点（Lesson 0001 §8）

配置作用注意
upstream + server 服务名:端口定义实例池服务名走 Docker 内置 DNS，不写死 IP
ip_hash;sticky：同 IP 固定同实例NAT 后多用户挤一实例；生产用 hash $cookie_…; 按会话粘
proxy_pass http://池名;反向代理转发容器端口是 3000，不是宿主映射的 3001/3002
proxy_buffering off;流式响应不被缓冲SSE / chunked（对话进度推送）必开
proxy_read_timeout 300s;读超时放宽默认 60s 会掐断长回答 + GLM 退避（~63s 窗口）
log_format … $upstream_addr日志记下每个请求去了哪台（0003）多实例排查的第一双眼睛；docker compose logs nginx 直接可见
nginx -s reload不中断服务地重读配置（0003）新 worker 接客、旧 worker 干完再退；配置有错则旧配置继续生效。容器里：docker compose exec nginx nginx -s reload
server … weight=N;权重分流 / 灰度（0003）与 ip_hash 叠加时分的是"用户"而非"请求"
proxy_next_upstream失败换台（默认 error timeout）POST 默认不换台（非幂等，需显式 non_idempotent）——发布前先摘流量排空
