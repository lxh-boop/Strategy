Lesson 0002 · 多实例部署

流量从哪来：入口、端口与你的服务名单

概念约 20 分钟 + 动手谱（前置：装好 Docker，见 Redis 轨 0002） · 前置 Lesson 0001 · 共享术语表
归档说明本页已并入对应的面试课，作为实操参考谱保留：面试讲项目前把它跑通，项目故事才经得起追问。交互式自评见主课页面。

1 · 你天天在用的"转发程序"

先看一段你自己的代码——factor-agent-react/vite.config.ts：

server: {
  port: 5173,
  // 开发期跨域代理：前端所有 /api 请求转发到本地 NestJS 后端（factor-agent-server）
  proxy: { "/api": "http://localhost:3000" },
}

开发时你打开 localhost:5173，页面里发的 /api/... 请求其实是 Vite 这个程序接住、再转给 3000 端口的后端的——画出来：

【开发模式（今天）】

浏览器 ──:5173──> Vite dev server ──proxy /api──> server 容器/进程 :3000
        <──页面+静态资源──┘
点破 Vite 的 proxy 就是一个"转发程序"——你其实天天在用上一课讲的那个角色，只是它藏在开发工具里。上节课的困惑"nginx 是什么"，答案就是：生产环境里干 Vite proxy 这件事的程序，因为生产环境没有 Vite。

npm run build（vite build）之后，React 代码变成一堆静态文件（dist/ 目录），Vite 退场。这时出现两个空缺：

  1. 谁把 dist/ 里的静态文件发给浏览器？（Vite 之前干的活）
  2. 谁把 /api 请求转发给后端？（Vite proxy 干的活）

补上这两个空缺的，就是 nginx——一个程序补两个空缺。而且上一课你已经见过它的部署方式：也是一个 Docker 容器。

2 · 端口五分钟：门牌与接线

IP 是楼，端口是门牌。一台机器上每个监听的程序占一个门牌，浏览器访问 IP:端口 就是"按门牌找程序"。你的项目现在已经用了一串门牌：

门牌谁在用给谁看
:5173Vite dev server只有开发者（生产不存在）
:3000factor-agent-server（容器内监听）本机/内网
:3001 / :3002两个 server 容器的宿主映射（0001 的 -p）本机调试
:8080入口 nginx 容器（-p 8080:80）所有用户

-p 3001:3000 这种写法是两套门牌之间的接线：容器有自己的门牌系统（隔离的），-p 宿主:容器 把宿主的 3001 接到容器的 3000。所以多实例才能共存——容器里都监听 3000，宿主机上各接各的门牌。

上完线后只有一个门牌对用户公开：:8080（入口 nginx）。其余全是内部接线——这就是"固定入口"的含义：实例可以加可以减，用户手里的地址永远不变。

3 · 前端去哪了：静态文件装进 nginx

回答上次的表格：前端不需要"跑着的容器"。vite build 的产物是静态文件——文件不是程序，不需要进程跑它，nginx 顺手就能发。所以入口 nginx 一份配置干两件事：

server {
    listen 80;
    root  /usr/share/nginx/html;      # ← 前端 dist/ 就放在这里
    index index.html;

    # 职责一：/api 开头的请求 → 转发给后端实例池（接替 Vite proxy）
    location /api {
        proxy_pass http://factor_server;      # 0001 定义的 upstream（server-a/b + ip_hash）
        proxy_http_version 1.1;
        proxy_buffering off;                  # 流式响应三件套（0001 §8 讲过）
        proxy_cache off;
        proxy_read_timeout 300s;
    }

    # 职责二：其余所有请求 → 直接发前端静态文件
    location / {
        try_files $uri /index.html;           # SPA 保险，见 §5
    }
}

你们的完整服务名单（这就是整个系统的全部容器）：

程序容器数职责
nginx（带前端文件）1唯一入口：发前端 + 转 /api + sticky
factor-agent-serverN（2 起步）GLM 对话、回测——重活和状态都在这
redis1（0004 课接入）将来的共享状态
MySQL0公司现成库，容器名单之外
分离形态的存在理由 前端也可以做成独立容器（再起一个装着 dist 的 nginx），入口 nginx 只做转发——那叫分离形态，只在前后端团队要独立发布、独立扩缩时才值得。你们 100 人规模、一两个人维护：单 nginx 形态是正解，别给自己加一跳。

4 · 动手谱：把前端装进入口

动手（前置：Docker 已装 + 0001 的 deploy-lab 目录） 目标：把 0001 里"裸 nginx"入口升级为"带前端的 nginx"。四步，每步有预期结果。
  1. 在 factor-agent-react/ 新建 Dockerfile（两段式：node 段跑 vite build，nginx 段装产物）： 
    FROM node:22-bookworm-slim AS build
WORKDIR /app
COPY package-lock.json package.json ./
RUN npm ci
COPY . .
RUN npm run build            # vite build → dist/

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

    同目录 .dockerignore：node_modules、dist。nginx.conf 就是 §3 那份，放到这个目录里。

    注意：upstream 定义（factor_server / ip_hash / server-a/b）要一起写进这份 nginx.conf——每个 nginx 容器只认自己的配置文件。
  2. 改 deploy-lab/compose.yaml 的 nginx 服务： 
      nginx:
    build: ../factor-agent-react      # 从"裸 nginx 镜像"换成"带前端的镜像"
    ports:
      - "8080:80"
    depends_on:
      - server-a
      - server-b
    restart: unless-stopped
    # 原来的 volumes 挂载 conf 那两行删掉——配置已 COPY 进镜像
    server-a / server-b / redis 三个服务原样不动。
  3. 整套重建： 
    docker compose up -d --build
    --build 强制重 build 有 build: 的服务。首次几分钟。
  4. 三连验证： 
    浏览器开 http://localhost:8080     → 应看到你的前端页面（不再是 nginx 欢迎页）
F12 网络 → 页面里的 /api 请求      → 同源（8080），不再跨域
docker logs server-a / server-b    → 操作几下页面，请求出现在其中之一的日志里，
                                     换个浏览器再试，大概率落在同一实例（ip_hash 生效）
    第三步的彩蛋见下框。
验证时你会撞见一个旧朋友的消失 你后端 main.ts 里的 app.enableCors() 是为开发期 Vite(5173) 跨域开的。现在前端和 /api 同在 8080 下——同源了，浏览器的跨域拦截根本不触发。CORS 配置可以省（留着也无害）。这就是"入口统一"的隐藏红利。

5 · SPA 保险：刷新 404 的由来

try_files $uri /index.html; 这行防的是一件事：如果你的前端用了前端路由（React Router 之类），用户停在 /strategies/xxx 页面按 F5——浏览器向服务器要 /strategies/xxx 这个路径的文件，而服务器上根本没有这个文件（它只存在于浏览器里的 JS 路由）→ 404。try_files 的意思是"找不到就发 index.html"，让前端路由接管。就算你现在没用路由库，这行也是 SPA 的标准保险，白写不亏。

6 · 检索练习

Q1 · 开发期把 /api 转发给后端的是 Vite proxy；生产环境接替这个角色的是——

回忆 §1：Vite 在 build 后退场，proxy 的活必须有人接。生产环境里那个"转发程序"叫什么？
对。入口 nginx 的 location /api + proxy_pass 接替 Vite proxy——它就是生产环境的转发程序，顺带还接管了 Vite 发静态文件的活。

Q2 · -p 8080:80 里两个数字的关系是——

回忆 §2：两套门牌之间的接线。浏览器在宿主机的 8080 上找到 nginx，nginx 自己在容器里监听多少？
对。宿主 8080 接容器 80——用户只看宿主门牌，容器门牌是内部世界。多实例共存靠的就是这套接线各接各的。

Q3 · SPA 部署后，用户在子页面按 F5 收到 404，原因是——

回忆 §5：前端路由的"页面"存在哪里？服务器按路径找文件时能找到吗？
对。子页面的"页面"只存在于浏览器里的 JS 路由，服务器上没有对应文件——try_files 兜底发 index.html，让前端路由接管路径。

Q4 · 你们的规模下前端不需要 N 个容器，决定性原因是——

回忆规则："几个容器看它扛不扛得住"。nginx 吐静态文件的承载力是什么量级？你们用户量离它差多远？
对。nginx 发静态文件是万级并发的承载力，100 人的流量差着四个数量级——复制前端容器毫无必要。真正需要 N 个的是干重活、有状态的后端。

Q5 · 前端与 /api 同源之后，下列哪项可以直接省掉——

回忆 §4 结尾的提示框：enableCors 当初是为了谁开的？同源之后浏览器的哪种拦截不再触发？
对。enableCors 是为开发期 Vite(5173) 跨域开的；同源后浏览器的跨域拦截不触发，CORS 可省。入口统一带来的隐藏红利。
