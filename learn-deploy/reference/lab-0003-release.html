Lesson 0003 · 多实例部署

滚动更新与零停机发布

概念约 20 分钟 + 动手谱（前置：0002 动手跑通） · 前置 Lesson 0002 · 命令速查表 · 共享术语表
归档说明本页已并入对应的面试课，作为实操参考谱保留：面试讲项目前把它跑通，项目故事才经得起追问。交互式自评见主课页面。

1 · 单实例的发布之痛

你今天发布新版后端的动作是：改代码 → npm run build → 重启 node 进程。单实例下这一重启意味着：

重启瞬间：
  正在跑的 GLM 对话 → 连接被掐断 → 前端 90 秒看门狗报错
  正在跑的回测     → 半途而废
  所有用户         → 从"重启"到"就绪"期间全部请求失败

人少、深夜发布、手快，这窗口可以忍。但多实例的全部意义就在于：这个窗口可以缩短为零——因为你有两台，可以让一台休息时另一台值班。这一课讲的就是这套值班交接的规矩。

2 · 滚动更新：一台一台上，永不全体离场

「滚动更新」（rolling update）的本质简单到一句话：任何时候至少有一个实例在服务，另一个才被允许更新：

【发布前】   A: v1 ──┐
                     ├── nginx ──> 用户
             B: v1 ──┘

【窗口期】   A: v2（重启中 → 就绪）
             B: v1 ──── 扛住全部流量
【完成后】   A: v2
             B: v2

落到 compose，主谱就三条命令（语义都已在 compose up 官方参考核实）：

docker compose build server-a                  # 只构建 A 的新镜像
docker compose up -d --no-deps --wait server-a # 只动 A：重建并等它健康
# 验证 A 正常后，对 B 重复上面两步
旗标含义为什么必须
--no-deps不动它依赖/关联的服务你要的是"只重启 A"，不是全家跟着动
--wait阻塞到服务健康检查通过才返回0001 §7 配的 healthcheck 在这里收账：命令返回 = 新实例真的能接客了
末尾的 server-a只操作指名的服务compose 的惯例：命令末尾点名谁就动谁，不点名 = 全家

窗口期的真相：GET 和 POST 待遇不同

这条是本课最重要的真实细节（出自 nginx proxy_next_upstream 官方文档）：

nginx 的自动换台只覆盖一半请求 proxy_next_upstream 默认值是 error timeout——转发失败/超时时换下一台重试。但这条默认只安全适用于幂等请求（GET）；POST 属于非幂等请求，默认不会自动换台（要显式加 non_idempotent 才会，且响应已开始发送就无法补救）。你们的对话请求恰恰是 POST——重启 A 的那一两秒里，恰好打到 A 的在途对话会失败，nginx 不会替它换台。

所以诚实版的账目是：简化滚动更新的停机影响 = 「容器重建那几秒」里「恰好打向该实例」的在途 POST。窗口秒级、影响面是个别请求，比单实例的"全体中断几十秒"已是天壤之别——但离"零"还差一步，补齐它的是 §3 的舞步。

3 · 优雅发布进阶：摘流量 → 排空 → 重启 → 请回

先修一个 0002 留下的前提 0002 把 nginx.conf COPY 进了镜像——配置跟着镜像走、不可变，适合发布；但这样你在宿主机改配置文件，容器里根本看不到，舞步跳不起来。运维要现场改分流，所以生产常见的分工是：前端文件烤进镜像，upstream 配置挂载出来。§6 动手谱第 0 步会把配置改回挂载（挂载会覆盖镜像里同路径的那份）。

把 POST 的那点损失也消掉，办法是在重启之前：先让 nginx 不再往 A 发新请求，等 A 手头的活干完（排空，drain），再放心重启。nginx 有个配合这个流程的妙命令——reload：不中断服务地重读配置（master 起新 worker 接客，旧 worker 干完手头的活再退场，配置有错则原配置继续生效）。

# ① 摘流量：编辑 nginx.conf，注释掉 server-a 那一行
#    server server-a:3000;   ← 前面临时加 #

# ② 不中断地让 nginx 按新配置分流
docker compose exec nginx nginx -s reload

# ③ 排空：盯 docker logs -f server-a，直到在途请求干完、日志安静

# ④ 放心重启/换版 A
docker compose up -d --no-deps --wait server-a

# ⑤ 请回：去掉注释，再 reload 一次
docker compose exec nginx nginx -s reload

这套舞步在你们规模下是发布的标准姿势；k8s 里的滚动策略（自动摘除、自动排空）不过是把这几步自动化了——你现在手练的就是那个自动化的手动版。

4 · 窗口期的数据库纪律

滚动更新期间存在一段v1 和 v2 同时连着同一个库的窗口（§2 图的中间状态）。代码可以两版共存，前提是数据库迁移向后兼容——旧代码碰新表结构不能炸。三条纪律：

纪律原因
只加不改删：新列可空或带默认值旧代码不认识新列——列在，它当不存在，无害；若你把旧列改名/删掉/改成 NOT NULL，旧代码的 INSERT/SELECT 立刻崩
改名/删除 = 拆成多次发布加新列 → 两版并存过渡 → 全量上新版后，下个发布才删旧列（扩张 → 迁移 → 收缩，expand-migrate-contract）
迁移必须幂等启动时自动执行迁移的话，两版各自启动都要能安全重跑
你们已有的好习惯 你们代码里的 ensureFactorUsageTable()（启动时 CREATE TABLE IF NOT EXISTS）就是幂等迁移——跑一百遍和跑一遍结果相同，滚动窗口里两版各自启动都安全。这个模式值得推广到所有启动期迁移。

反例（在窗口期必炸）：一条 ALTER TABLE runs CHANGE old_col new_col BIGINT;——v1 还在按 old_col 读写，改完名的瞬间它全线报错。正确姿势是加新列 → 双写过渡 → 下个版本删旧列。

5 · 灰度发布：把"出新版"变成"试探出新版"

上次聊企业分流时欠你的另一半，在这里补上。灰度的核心思想：新版不用一次全量，先让一小部分流量试水，看着没问题再放开。

第一档：手动金丝雀（50% 试水）

最朴素的灰度就是 §2 主谱本身——只更新 A，B 留在旧版，观察半天：docker logs 里的报错率、GLM 限流频率、用户反馈。没问题再更 B。这已经是金丝雀发布的全部精髓：让旧版当安全网。

第二档：权重灰度（按比例试探）

想让新版只接 25% 流量，nginx 的 weight 一行搞定：

upstream factor_server {
    ip_hash;
    server server-a:3000 weight=1;   # 新版：每 4 次请求接 1 次
    server server-b:3000 weight=3;   # 旧版：扛 75%
}

观察无异常 → 调成 1:1 → 全量后摘掉 weight。回滚 = 反向调权重，秒级。

概念备忘：蓝绿发布

还有一种「蓝绿发布」：整套新环境（蓝）先建好，验证后在入口一刀切流。它换来的是"切换瞬间的确定性"，代价是双倍资源。你们两台容器的规模用不上——但面试和方案讨论里会见到这个词，你知道它和金丝雀的区别（整批切 vs 按流量逐步）就够了。

回滚纪律：镜像标签

发现 v2 有 bug 要退回，正确的姿势不是"翻出旧代码重新 build"（慢，且依赖可能已漂移、构建可能失败），而是切回旧镜像标签。给 compose 加一个版本旋钮：

# compose.yaml —— 两台都换成带版本旋钮的镜像名
  server-a:
    build: ../factor-agent-server
    image: factor-server:${RELEASE:-0.1}
  server-b:
    image: factor-server:${RELEASE:-0.1}
RELEASE=v2  docker compose build server-a                   # 构建并打上 v2 标签
RELEASE=v2  docker compose up -d --no-deps --wait server-a  # 只把 A 换成 v2
RELEASE=0.1 docker compose up -d --no-deps --wait server-a  # 回滚 = 秒级切回旧 tag
版本旋钮的一个暗坑 ${RELEASE:-0.1} 的意思是"没设就用 0.1"——所以发布完成后，任何一次忘带变量的裸 docker compose up -d 都会把两台悄悄拉回 0.1。解法：把当前版本写进 deploy-lab 目录下的 .env 文件钉住（RELEASE=v2），compose 会自动读它做变量替换。注意这个 .env 和 env_file: 注入容器的那份是两回事：前者喂给 compose.yaml 里的 ${...}，后者喂给容器里的程序。

纪律一句话：每次发布打新 tag，旧 tag 永远留着——回滚的底气是"旧版本一直躺在本地镜像库里"，不是"我记得怎么把它再造出来"。

6 · 动手谱：亲手滚一次

动手（前置：0002 跑通，整套 compose 在跑） 目标：亲手制造一次 v1 → v2 的滚动更新，亲眼看到窗口期，再演练回滚、舞步和灰度。每步都标了预期结果——对不上就把输出带给 agent。
  1. 第 0 步 · 补齐四处前提（编辑 deploy-lab/compose.yaml 与 factor-agent-react/nginx.conf）： 
    # ① compose：server-b 补上和 server-a 一模一样的 healthcheck 块（0001 只给 A 写了）
# ② compose：server-a / server-b 的 image 都改成 factor-server:${RELEASE:-0.1}（§5）
# ③ compose：nginx 服务把配置挂出来（§3 前提，挂载覆盖镜像里那份）
  nginx:
    build: ../factor-agent-react
    volumes:
      - ../factor-agent-react/nginx.conf:/etc/nginx/conf.d/default.conf:ro

# ④ nginx.conf：让 nginx 在日志里记下每个请求去了哪台
#    文件最顶部（server 块之外）加：
log_format upstream '$remote_addr -> $upstream_addr "$request" $status';
#    server { 块内第一行加：
access_log /var/log/nginx/access.log upstream;
    再在 deploy-lab 目录建 .env，写一行 RELEASE=0.1，然后 docker compose up -d 应用。 docker compose ps：两台 server 都显示 (healthy)。docker compose logs nginx --tail 5 里每行都带 -> 172.x.x.x:3000——这是你以后排查多实例最可靠的眼睛（0002 的 sticky 验证也可以用它）。
  2. 制造一个看得见的 v2：把 factor-agent-server/src/main.ts 里的 setTitle('因子智投 API') 改成 setTitle('因子智投 API v2')。 此刻只改了源码，两个容器跑的都还是旧镜像。
  3. 构建 v2，只上 A： 
    RELEASE=v2 docker compose build server-a
RELEASE=v2 docker compose up -d --no-deps --wait server-a
    第二条命令会停顿到 A 的健康检查通过才返回——--wait 在收账。
  4. 亲眼看窗口期： 
    docker compose ps
    IMAGE 列：server-a 是 factor-server:v2，server-b 还是 factor-server:0.1——两版同时在线，就是 §2 图里的中间状态。浏览器开 localhost:8080/api/docs，大标题是哪个版本，取决于 ip_hash 把你分给了谁。
  5. 上 B，关闭窗口，钉住版本： 
    RELEASE=v2 docker compose up -d --no-deps --wait server-b
    然后把 .env 改成 RELEASE=v2。 B 不用再 build——v2 镜像第 3 步已经造好了。ps 里两台都是 v2。
  6. 回滚演习（假装 v2 有 bug）： 
    RELEASE=0.1 docker compose up -d --no-deps --wait server-a
    几秒后 A 回到 0.1——没有重新 build 任何东西，旧 tag 一直躺在本地。演完用同样的命令把 A 切回 v2。
  7. 进阶 · 优雅舞步：照 §3 的五步对 A 完整跳一遍。在第 ② 步 reload 之后，连打几次请求再看日志： 
    for i in $(seq 10); do curl -s -o /dev/null localhost:8080/api/docs; done
docker compose logs nginx --tail 10
    最近 10 行的 upstream 地址只剩一个 IP——A 已被摘掉，请求全去了 B。想确认哪个 IP 是谁：docker compose exec server-a hostname -i。
  8. 进阶 · 权重灰度：nginx.conf 改成 §5 的 weight=1 / weight=3，临时注释掉 ip_hash;，reload 后统计分布： 
    docker compose exec nginx nginx -s reload
for i in $(seq 20); do curl -s -o /dev/null localhost:8080/api/docs; done
docker compose logs nginx --since 1m | grep -oE '[0-9.]+:3000' | sort | uniq -c
    两个 IP 的计数约 5 : 15。为什么要临时去掉 ip_hash：你本机只有一个 IP，ip_hash 会把你钉在一台上。这也揭示一个要点——ip_hash + weight 分的是"用户"而不是"请求"：同一用户始终落在同一版本，这恰恰是灰度想要的。做完记得把 ip_hash; 恢复。

7 · 发布前三问

每次敲 up -d 之前，过一遍 ① 这次发布的数据库迁移向后兼容吗？（v1 窗口期要活下来）
② 镜像打 tag 了吗？（出事要能秒回）
③ 健康检查通过了吗？（--wait 返回了再动下一台）

8 · 检索练习

Q1 · 只更新 server-a 期间（server-b 没动），用户请求的表现是——

回忆 §2 的三张状态图：A 重启期间谁在值班？「一半中断」错在哪——nginx 只会把请求发给健康检查认为活着的实例。
对。B 全程值班，集群层面无中断——多实例把「发布 = 停机」改写成了「发布 = 少一台轮值」。个别在途请求的损失见 Q5。

Q2 · v1/v2 窗口期最容易打崩系统的一件事是——

回忆 §4：窗口期两版代码同时连同一个库。旧代码最怕新代码对数据库做了什么？
对。改列名/删列/加 NOT NULL 都会让 v1 的 SQL 立刻全线报错——迁移向后兼容是滚动更新的第一纪律。

Q3 · 给表加一列可空字段，v1 旧代码——

回忆 §4 第一条：旧代码不认识新列——列在它会怎么样？这正是"只加不改删"能成立的原因。
对。旧代码 SELECT 时要么按列名拿（新列根本不出现在结果里），要么拿到 NULL——都无害。可空/带默认值，是"只加"能安全成立的前提。

Q4 · 发现 v2 有 bug 要回滚，正确操作是——

回忆 §5 回滚纪律：为什么"重新 build 旧代码"不可靠？"回滚数据库"违反了迁移的哪条铁律？
对。切 tag 秒级且确定；重新 build 慢且依赖可能漂移；而数据库迁移只进不退——删掉的列回不去。所以「只加不改删」纪律加上「留旧 tag」纪律，共同保证回滚永远可行。

Q5 · 重启 server-a 的瞬间，一个在途的用户对话 POST 请求会——

回忆 §2 的警告框：proxy_next_upstream 默认值只覆盖哪类请求？你们的对话请求是哪类？
对。默认 error timeout 只对幂等请求换台，POST 不在其中——这正是 §3「摘流量→排空→重启→请回」舞步存在的全部理由。GET 请求则默认自动换台，用户无感。
