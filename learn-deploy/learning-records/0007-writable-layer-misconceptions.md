# 误解纠正：可写层不是"暂存区"，"写操作"指运行时文件写入

用户读 0001 q02 时暴露两个误解：① 以为可写层写完之后还要同步到一个"真实的容器"里；② 把"写操作"理解成程序员改代码或数据库写入，因而不明白为什么需要可写层。纠正：容器 = 镜像只读层 + 自己的可写层（合并视图）+ 进程，可写层就是改动的终点（stop/start 保留、rm 即丢、不回写镜像、同镜像其他容器看不到）；"写"指程序运行时写文件（日志、临时文件、exec 进去改的配置）——代码在 build 时进只读层，数据库写入是发给 MySQL 进程的网络请求。

Evidence: 2026-11-02 用户原话："在可写层写完之后呢？还在真实的容器中修改吗？""如果是代码的写操作，这不是程序员的事情吗？为什么要加一个可写层，什么情况下会使用"。
Implications:
- 0001 q02 原措辞"所有写操作发生在这里"太抽象，已改写并补两道追问 + 项目故事（logs/、memories/ 挂卷）；q08 挂载类型同步修正为官方五种中的常用三种。
- 盲区在"构建期 vs 运行期"的边界。后续讲卷、无状态化、不可变基础设施、Redis 持久化（RDB/AOF 写的是 Redis 进程自己的文件）时，先用一句话交代"谁在写、写到哪、什么时候写"。
- 本次选用的类比：JS 原型链（读先找自身再沿原型找；写只落自身、不改原型）——贴合用户 TS 背景，效果待验证。
- 待验证：用户能否自己说清"logs/ 为什么要挂卷"——下次作为检索题。
